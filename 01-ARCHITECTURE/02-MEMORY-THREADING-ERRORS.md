# Память, время жизни ресурсов и ошибки

Основа: присланный **After Effects SDK 25.6 build 61**. Сверка: **2026-10-01**. Пути ниже относительны `Examples/`; идентичность исходников и границы проверки записаны в [обзоре памяти и MFR](../18-SDK-HEADER-TOOLS/07-MEMORY-MFR-SDK25.6.md).

Здесь объясняются контракты из headers и конкретных образцов SDK. Рекомендации по архитектуре выделены отдельно. Глава не сообщает о новом запуске AE, проверенной утечке или готовом native-считывателе.

## 1. Сначала определить, чем именно мы владеем

Указатель, handle и право временного доступа — разные вещи. Например, `AEGP_GetReceiptWorld` возвращает read-only world, которым плагин не владеет. Освобождать следует получение кадра через `AEGP_CheckinFrame`, а не сам world. Напротив, world, созданный нашим вызовом `PF_NewWorld`, имеет парный `PF_DisposeWorld`.

Источники: `Headers/AE_GeneralPlug.h:5355–5391`; `Headers/AE_EffectCBSuites.h:430–451`.

| Полученный ресурс | Что заканчиваем | Что нельзя подменять |
|---|---|---|
| Suite из `SPBasicSuite::AcquireSuite` | `ReleaseSuite` с теми же именем и версией | Не освобождать таблицу функций через `delete` |
| Собственный `PF_Handle` из `host_new_handle` | `host_dispose_handle`; собственный lock имеет отдельный unlock | Unlock не освобождает выделенную память |
| Собственный `AEGP_MemHandle` | `AEGP_FreeMemHandle`; lock/unlock — отдельная пара | Не смешивать с PF-handle API |
| Собственный `PF_EffectWorld` из `PF_NewWorld` | `PF_DisposeWorld` | Не применять к входному/выходному world, выданному host |
| `AEGP_StreamRefH`, который API требует вернуть | `AEGP_DisposeStream` | Наличие суффикса `H` не делает объект memory handle |
| `AEGP_EffectRefH`, который API требует вернуть | `AEGP_DisposeEffect` | Это не `AEGP_DeleteLayerEffect`, удаляющий эффект со слоя |
| Полученный `AEGP_FrameReceiptH` | `AEGP_CheckinFrame` | Не освобождать заимствованный world отдельно |
| Успешно выданный auxiliary chunk | `PF_CheckinLayerChannel` | Не переносить сюда необязательность раннего SmartFX checkin |
| Compute Cache receipt | `AEGP_CheckinComputeReceipt` до возврата host | Не удалять cache value самостоятельно |

Источники таблицы: `Headers/SP/SPBasic.h:82–101`; `Headers/AE_EffectCBSuites.h:52–78,430–451`; `Headers/AE_GeneralPlug.h:881–909,1487–1500,2170–2180,5355–5391`; `Headers/AE_ChannelSuites.h:67–87,545–558`; `Headers/AE_ComputeCacheSuite.h:138–167`.

**Рекомендация Библии:** рядом с каждой операцией получения ресурса записывать владельца, срок доступа и способ завершения. Не создавать общий deleter, выбирающий освобождение по внешнему сходству типов. Для каждой семьи нужен собственный контракт.

## 2. Handle: выделение, доступ и освобождение

`PF_HandleSuite1` содержит операции создания, блокировки, разблокировки, определения размера, изменения размера и уничтожения handle. У `host_resize_handle` передаётся адрес handle: комментарий прямо предупреждает, что значение handle может измениться. Поэтому копия старого handle или ранее полученного адреса не становится автоматически пригодной после resize.

Есть легко пропускаемая деталь: в этой поставке **`kPFHandleSuiteVersion1` равен 2**, хотя имя структуры и имя макроса заканчиваются на `1`. Для acquisition берём макрос из header, а не вычисляем версию по суффиксу типа. Это особенность данной декларации, не универсальное правило нумерации suites.

Источник: `Headers/AE_EffectCBSuites.h:52–78`.

Для самостоятельно созданного временного handle рекомендуемый порядок такой:

```text
проверить размер
→ выделить handle и проверить результат
→ получить адрес и проверить результат
→ работать только в выделенных границах
→ закончить собственный доступ
→ уничтожить собственный handle, если владение не передано
```

В AEGP используется другая семья: `AEGP_NewMemHandle`, `AEGP_LockMemHandle`, `AEGP_UnlockMemHandle`, `AEGP_FreeMemHandle`. Lock в её декларации помечен как nestable. Там же есть операции memory reporting и статистики. Они относятся к этой API-семье: из их наличия не следует полный учёт всех выделений сторонних библиотек и GPU.

Источник: `Headers/AE_GeneralPlug.h:868–909`.

**Различие понятий:** lock memory handle здесь обеспечивает доступ к памяти. Это не объявление критической секции между render-потоками. Вопрос конкурентного изменения данных отдельно регулируется MFR-контрактом; см. [многокадровый рендер](../02-EFFECT-PLUGINS/04-MFR-THREAD-SAFETY.md).

## 3. Не разблокировать за host его sequence handle

Для обычной передачи `sequence_data` header говорит: перед вызовом плагина handle уже заблокирован, а его lock-state восстанавливает host. Там же дано предупреждение о повторном входе при arbitrary data: собственная пара lock/unlock внутри такого вызова может преждевременно разблокировать handle. Исключение отдельно описано для `SEQUENCE_SETUP`: только что выделенный нами handle ещё не заблокирован.

`global_data` и `frame_data` в соответствующих комментариях отсылают к такому же автоматическому управлению lock-state. Это **не разрешение менять данные из любого потока** и не указание самостоятельно освобождать все выданные адреса.

Источник: `Headers/AE_Effect.h:2839–2848,2858–2903`.

Правило нужно читать вместе с MFR: при `PF_OutFlag2_SUPPORTS_THREADED_RENDERING` документирован другой способ чтения sequence data во время render, а `in_data->sequence_data` указан как `NULL`. Нельзя взять старый пример разыменования этого поля и объявить его универсальным для threaded render.

Источник: `Headers/AE_Effect.h:912–935`; `Headers/AE_GeneralPlug.h:5707–5718`.

## 4. Global, sequence, frame и pre-render — не четыре названия одного хранилища

| Данные | Контракт из SDK | Рекомендация для собственного эффекта |
|---|---|---|
| `global_data` | Создаётся при global setup; выделенное освобождается при global setdown | Хранить общие неизменяемые таблицы и явно управляемые общие ресурсы, не «текущий кадр» |
| `sequence_data` | Создаётся/восстанавливается для экземпляра; имеет сохранение, дублирование и setdown | Отделять пользовательское состояние от временного render-кэша |
| `frame_data` | Поле классического `FRAME_SETUP`; не записывается на диск | Не превращать его в универсальную замену SmartFX state |
| `pre_render_data` | Указатель передаётся из pre-render в render; предусмотрен callback удаления | Передавать самостоятельный снимок нужных данных, а не указатель на стек pre-render |

Источники: `Headers/AE_Effect.h:1065–1077,1084–1142,2839–2903,2501–2523,2563–2572`.

**Рекомендация Библии:** временный массив для одной обработки держать в локальном объекте этого вызова. Долгоживущий кэш оправдан, только когда известны его ключ, владелец, предел размера и момент уничтожения. Само слово «кэш» не продлевает срок жизни указателей на входные пиксели.

## 5. Сохранение sequence data: две разные операции

### `SEQUENCE_FLATTEN`

Исторический flatten преобразует рабочее состояние в плоское: header требует освободить прежнее unflat-состояние и вернуть новое flat-состояние через `out_data->sequence_data`. Вложенные handles требуют соответствующего флага `PF_OutFlag_SEQUENCE_DATA_NEEDS_FLATTENING`.

Источники: `Headers/AE_Effect.h:1104–1113,2873–2889`.

### `GET_FLATTENED_SEQUENCE_DATA`

Этот selector возвращает **независимое выделение**, пригодное для сохранения или инициализации другого экземпляра. Владение возвращённым handle передаётся host. Это не команда уничтожить рабочее состояние UI-экземпляра. Поддержка обозначается `PF_OutFlag2_SUPPORTS_GET_FLATTENED_SEQUENCE_DATA`.

Header отдельно требует учитывать `NULL` при resetup и допускает flat data при setdown. Поддержка нового selector не позволяет предполагать, что каждый setdown получает один и тот же внутренний layout.

Источник: `Headers/AE_Effect.h:1115–1142`.

### Что показывает PathMaster

В `Effect/PathMaster/PathMaster.cpp:186–220` исторический `SequenceFlatten` копирует значения, удаляет вложенную строку и старый sequence handle, затем возвращает flat handle. В `:233–267` `GetFlattenedSequenceData` создаёт отдельную копию, но намеренно не удаляет исходные данные. `SequenceSetdown` в `:167–181` различает flat/unflat перед освобождением вложенной строки.

Это полезный пример **разницы владения**, а не универсальный сериализатор. В resetup самого образца есть предупреждение `NOT X-PLATFORM SAFE` при переносе значения (`:300–303`). Не выдаём его текущий layout за проверенный межплатформенный формат.

**Рекомендация проектирования:** сериализовать содержимое, а не адреса строк, handles, mutex или объектов GPU. В плоском формате явно хранить версию и размеры, проверять вход до разыменования, а рабочие объекты восстанавливать отдельно. Успешное чтение структуры компилятором не заменяет save/reopen и migration-тесты.

## 6. SmartFX state и четыре разных cleanup-контракта

`PF_PreRenderOutput` содержит `pre_render_data` и `delete_pre_render_data_func`. Комментарий связывает eventual deletion именно с этим callback, если он задан. Нельзя рассчитывать на уничтожение произвольного C++ объекта лишь потому, что его адрес присвоен `void*`.

Источник: `Headers/AE_Effect.h:2501–2523`.

**Рекомендуемый паттерн:** подготовить snapshot под локальным владельцем; при успешной передаче зарегистрировать совместимый deleter и передать владение один раз. До передачи ошибки очищает локальный владелец, после передачи не должно быть второго независимого удаления. Snapshot не должен содержать ссылки на стек закончившегося вызова или заимствованные pixels за пределами их срока доступа. Это схема проектирования, не новый скомпилированный пример.

Не смешивать разные возвраты:

- Обычный `checkout_param` требует `checkin_param`; после checkin поля полученного `PF_ParamDef` недействительны (`AE_Effect.h:2669–2673`).
- Комментарий **конкретного SmartyPants** описывает автоматический checkin параметров, взятых в `SMART_PRE_RENDER`; в `SMART_RENDER` образец явно вызывает `PF_CHECKIN_PARAM` (`SmartyPants.cpp:399–403,965–989`). Это контекстное уточнение, не отмена всех cleanup-правил.
- SmartFX `checkout_layer_pixels` выдаёт pixels на время команды либо до раннего checkin; ранний `checkin_layer_pixels` прямо отмечен как необязательный способ раньше освободить память (`AE_Effect.h:2576–2583`).
- Auxiliary checkout требует `PF_CheckinLayerChannel` для предотвращения утечек (`AE_ChannelSuites.h:82–87,545–558`).

Входной SmartFX world, output world, auxiliary chunk и наш собственный scratch world нельзя складывать в контейнер с одним и тем же освобождением. Подробности получения областей вынесены в [SmartFX](../02-EFFECT-PLUGINS/03-SMARTFX.md), auxiliary-данных — в [отдельную главу](../02-EFFECT-PLUGINS/08-AUXILIARY-CHANNELS.md).

## 7. Почему cleanup должен выполняться и после ошибки

В поставке `AE_Macros.h` макрос `ERR` выполняет выражение только при ещё нулевом `err`. `ERR2` вычисляет своё выражение независимо от уже имеющейся ошибки, но заменяет основной код только если ошибки раньше не было. Поэтому оборачивание обязательного освобождения обычным `ERR` может пропустить освобождение после сбоя.

Источник: `Headers/AE_Macros.h:41–46`.

Учебная схема, не полный обработчик:

```text
получить ресурс
если получение успешно:
    выполнить основную операцию
    закончить получение независимо от результата операции
    если основная операция успешна, вернуть ошибку cleanup
    иначе сохранить первоначальную ошибку и отдельно записать сбой cleanup
```

**Рекомендация Библии:** хранить факт успешного acquisition отдельно от общего `err`. Последующая ошибка не означает, что ранее полученный ресурс исчез. Но не нужно и безусловно освобождать объект, который получить не удалось.

В PF API различаются отсутствие памяти, неверный callback, неверный параметр callback и пользовательская отмена. `abort` должен периодически проверяться длительной обработкой; если callback возвращает ненулевое значение, header требует вернуть его host. Отмену не следует маскировать кодом повреждённой структуры.

Источники: `Headers/AE_Effect.h:497–509,2682–2687`.

**Рекомендация на границе C++/host:** перехватывать исключения до выхода из exported entry point и отдельно на каждой callback-границе, которую позже вызывает host. Сначала гарантировать cleanup, затем преобразовать ошибку в контракт нужного PF/AEGP обработчика. Одна внешняя `try` не является защитой для callback, вызываемого после её завершения.

## 8. Что уже есть в коде Библии — и чего эти helpers не делают

Проверен исходный snapshot `fcfb0e32c14916b55c2bcdbe414d3d1b3f524eeb`:

- [PicaSuiteRef](../19-NATIVE-CODE-FOUNDATION/code/PicaSuiteRef.h) связывает acquisition/release, запрещает копирование и переносит владение при move. Но `SPBasicSuite` и строка имени suite остаются заимствованными. Они должны жить достаточно долго. `reset()` отбрасывает код `ReleaseSuite`.
- [AegpOwners](../19-NATIVE-CODE-FOUNDATION/code/AegpOwners.h) разделяет stream/effect/frame receipt/memory handle и их способы освобождения. Эти owners **не удерживают собственную ссылку на suite** и не управляют memory lock автоматически. Их `reset()` также отбрасывает ошибки освобождения.
- [HostCallbackGuard](../19-NATIVE-CODE-FOUNDATION/code/HostCallbackGuard.h) использует переданный вызывающим кодом fallback и возвращает перехваченный ненулевой `A_Err`. Он не знает, какие ресурсы успели выделиться, не классифицирует все C++ exceptions и не выполняет rollback проекта.

Практическое следствие: suite-holder должен пережить owner, который вызовет её при уничтожении. `release()` такого owner передаёт ответственность дальше, а не освобождает ресурс. Для проверки ошибок cleanup нужен явно наблюдаемый путь завершения: вызов destructor сам по себе не доказывает успешность host-функции.

Это review существующего кода, **не исправление helpers и не повтор native-тестов**. Их дальнейшая доработка подчиняется отдельным критериям плана; изложенное ограничение не скрывается за словом RAII.

## 9. Размеры, потоки и диагностика

**Рекомендации проектирования:** до выделения памяти проверять произведения размеров на переполнение, реальный stride и допустимые границы. Не выделять heap-объект для каждого пикселя. Не кешировать borrowed pointers после checkin. Сохранять достаточную диагностику для восстановления последовательности acquisition/cleanup: имя ресурса, операция, код ошибки, команда и идентификатор render-запроса.

Для гонок важно, что `PF_ITERATE` может распределять работу между потоками; `refcon` должен быть read-only или правильно синхронизирован. Поэтому «один кадр» не означает «один поток».

Источник: `Headers/AE_EffectCB.h:687–694`.

Не удерживать собственный блокирующий mutex через host checkout/callback — **консервативная рекомендация Библии**, а не дословный запрет для всех SDK-функций. В самом SDK есть конкретное предупреждение: layer checkout в `UPDATE_PARAMS_UI` отдаёт чёрный кадр, чтобы не провоцировать render и возможный deadlock (`AE_Effect.h:2661–2667`). Это ещё одна причина не использовать UI callback как замену render-транзакции.

## 10. Критерий понимания главы

Сквозной [Compute Cache receipt/error/cancel walkthrough](../02-EFFECT-PLUGINS/04-MFR-THREAD-SAFETY.md)
показывает resource acquired независимо от subsequent error; call-local rows не
разделяются между requests. [Bounded MFR incident](../22-PROJECT-CASE-STUDIES/ELASTICGRIDFX-PERFORMANCE-SCOPE-2026-10-07.md)
сохраняет UNKNOWN cause и six-run non-reproduction отдельно: отсутствие crash не
доказывает баланс receipt или causal repair.

Перед использованием ресурса разработчик должен уметь ответить: кто владелец; чем он освобождается; когда истекает адрес; какой поток может его использовать; что произойдёт после ошибки; передаётся ли владение host.

Минимальная **рекомендуемая**, пока не выполненная здесь проверка собственного эффекта: отказ каждого выделения, ошибка после успешного checkout, отмена, дублирование экземпляра, flat/unflat setdown, сохранение/открытие и закрытие проекта. В отчёте отдельно проверяют баланс ресурсов и конечные пиксели: отсутствие crash не доказывает отсутствие утечек.

Далее: [MFR и разделение состояния](../02-EFFECT-PLUGINS/04-MFR-THREAD-SAFETY.md). Полные критерии готовности Библии остаются в [COMPLETION-CHECKLIST](../COMPLETION-CHECKLIST.md).
