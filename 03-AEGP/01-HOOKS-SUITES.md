# AEGP: инициализация, hooks и suites

**Основа: присланный SDK 25.6 build 61. Редакция 2026-10-01.** Глава объясняет объявления `AE_GeneralPlug.h`, поведение утилит SuiteHandler и структуру Easy Cheese; отдельно разбирает существующий Bible MenuTool. [Реестр исходников и ограничений](../18-SDK-HEADER-TOOLS/08-REGISTRATION-AEGP-SDK25.6.md).

AEGP — интеграция с приложением через зарегистрированные callbacks и наборы функций. Не следует мысленно превращать его в Effect с другой категорией: его initializer не принимает PF_Cmd, а обычная команда меню не является пиксельным render callback. Различие видно непосредственно из двух типов точек входа в SDK и ресурсов образцов.

## 1. От описания модуля к работе инструмента

В [главе PiPL](../01-ARCHITECTURE/03-PIPL-AND-LOADING.md) рассмотрен AEGP-ресурс Easy Cheese: Kind AEGP и архитектурная запись EntryPointFunc. Header задаёт точный тип initializer — `AEGP_PluginInitFuncPrototype` — и указатель на него `AEGP_PluginInitFunc`.

`Examples/Headers/AE_GeneralPlug.h:4167–4176` описывает пять аргументов:

| Аргумент | Роль |
|---|---|
| `SPBasicSuite*` | Доступ к PICA acquisition/release |
| driver major/minor | Два числа, переданные host; не версия продукта |
| `AEGP_PluginID` | Выданный host идентификатор плагина |
| `AEGP_GlobalRefcon*` | Место для возвращаемого указателя; header говорит, что он передаётся hooks |

Учебное объявление удобно связывать непосредственно с SDK-типом:

```cpp
extern "C" DllExport AEGP_PluginInitFuncPrototype EntryPointFunc;
```

Так же объявлен initializer в `Examples/AEGP/Easy_Cheese/Easy_Cheese.h:36–37`. Это не определение функции и не готовый bundle. Include paths, entry.h, resource/link settings и тело initializer всё ещё необходимы.

Полезная дополнительная compile-time проверка собственной реализации:

```cpp
#include <type_traits>
static_assert(
    std::is_same<decltype(&EntryPointFunc), AEGP_PluginInitFunc>::value,
    "AEGP entry signature must match this SDK");
```

Это авторский учебный фрагмент; его target-platform компиляция в этой редакционной итерации **NOT RUN**. Он показывает проверку типа, а не проверку загрузки или ABI всех зависимостей.

## 2. Три разных вида идентификаторов

**Plugin ID** выдаётся initializer и передаётся в registration/utility API. **Command ID** получают через `AEGP_GetUniqueCommand` для конкретной команды. **Refcon** — указатель на собственные данные, которые callback должен получить обратно. Это не взаимозаменяемые значения.

У каждого hook есть два канала контекста. Первый аргумент — global refcon плагина, возвращённый initializer. Второй — refcon конкретного hook, переданный его registration-функции. Их типы намеренно различаются, например AEGP_GlobalRefcon и AEGP_CommandRefcon.

Основание: `AE_GeneralPlug.h:2699–2714,2747–2765,2871–2878,4169–4174`.

Рекомендация проектирования: длительно живущее ToolState хранит необходимые общие данные, а per-hook контекст используют только там, где он действительно нужен. Нельзя передавать адрес локальной переменной и ожидать, что он сохранится после выхода из initializer. Нельзя автоматически превращать plugin ID в pointer или command ID.

Отдельно: `AEGP_Command_ALL` равен **0** (`:2671–2673`). Это специальный запрос всех команд при регистрации, а не «создай новую команду» и не доказательство подписки на любые изменения проекта.

## 3. Получение suite: версия — часть контракта

PICA AcquireSuite принимает имя, числовую версию и адрес выходного указателя. ReleaseSuite использует ту же пару имя/версия. В SPBasic.h acquisition описан как увеличение счётчика ссылок; release — как его уменьшение. Не сохраняйте рабочий указатель, потеряв соответствующую lifetime-зависимость.

Источник: `Examples/Headers/SP/SPBasic.h:80–101`.

Особенно показательный пример этой поставки:

```text
тип:       AEGP_RegisterSuite5
имя:       kAEGPRegisterSuite
версия:    kAEGPRegisterSuiteVersion5
значение:  6
```

Это буквально записано в `AE_GeneralPlug.h:2742–2745`. Подстановка числа 5 из имени типа запросит не то, что запросил бы SDK macro. Для CommandSuite1 соответствующий macro действительно равен 1 (`:2866–2869`), но это не общее правило.

Если acquisition не удался, не приводите другую генерацию suite к ожидаемому типу. Практические варианты — понятный unsupported result либо заранее реализованный fallback под конкретную другую генерацию. Такой fallback тоже требует своей проверки.

### Что делает AEGP_SuiteHandler

SuiteHandler из SDK лениво запрашивает suite при первом accessor-вызове и хранит полученный указатель. Неудачный запрос приводит к MissingSuiteError; контракт этой функции требует завершиться исключением, а не вернуться как будто suite получена.

Источники: `Examples/Util/AEGP_SuiteHandler.h:32–49,268–278,443–463`; предоставленная реализация исключения — `MissingSuiteError.cpp:24–43`.

Его destructor вызывает ReleaseAllSuites (`AEGP_SuiteHandler.cpp:33–46`). Это освобождение acquisition-ссылок, **не unregister ранее установленных callbacks**. ReleaseSuite в этом utility не сохраняет код ошибки (`:61–65`); RAII удобен, но не превращает cleanup в подтверждённо успешную операцию.

Если проект использует эту утилиту, нужно подключить её реализацию и реализацию MissingSuiteError. Header прямо предупреждает о link error без последней. Это частая разница между «объявления нашлись» и законченной сборкой.

## 4. Команда меню: три независимые операции

Создание работающего пункта состоит как минимум из трёх частей:

```text
GetUniqueCommand → InsertMenuCommand → RegisterCommandHook
                                         + UpdateMenuHook для доступности
```

`AEGP_GetUniqueCommand` даёт command ID. `AEGP_InsertMenuCommand` помещает название в заданное меню и позицию. `AEGP_RegisterCommandHook` связывает обработчик с командой. Их отдельные объявления находятся в `AE_GeneralPlug.h:2747–2760,2866–2898`.

Поэтому пункт может существовать, но не выполнять действие; зарегистрированный callback может не иметь видимого пункта; корректно созданный пункт может быть отключён логикой update hook. Ни одно из этих наблюдений само по себе не доказывает неисправность загрузчика.

Для своей команды обычно достаточно регистрации конкретного command ID. Easy Cheese использует Command_ALL, а затем сравнивает поступившую команду со своей (`Easy_Cheese.cpp:332–348,442–446`). Это демонстрирует фильтрацию, а не требование всем плагинам перехватывать все команды.

## 5. Что должен делать CommandHook

Его контракт включает command, hook_priority, входной `already_handledB` и выходной `handledPB` (`AE_GeneralPlug.h:2699–2705`). Разделяйте эти два boolean: один описывает предыдущую обработку, другой — решение текущего callback.

Для собственной команды безопасная логика проектирования выглядит так:

```text
контекст отсутствует или инструмент не активен → ничего не делать
поступила не наша команда → не перехватывать
уже обработана, а повторная обработка не нужна → выйти
проверить актуальные условия → выполнить действие
сообщить результат и признак обработки по выбранному контракту
```

Это схема, не дополнительная функция SDK. В частности, соглашение «handled только после успеха» в MenuTool является политикой этого инструмента. Easy Cheese ставит handled до основной работы; нельзя выдавать один образец за единственную семантику любого command hook.

### Priority: не скрываем оговорку header

Enum содержит `AEGP_HP_BeforeAE` и `AEGP_HP_AfterAE`, однако возле аргумента callback написано «currently always AEGP_HP_BeforeAE» (`:2692–2705`). Оба факта относятся к поставке. Эта глава не утверждает, что AfterAE проверен в AE 25.6, и не обещает универсальный after-change observer.

Если архитектура зависит от точного момента вызова, требуется измерение конкретного сценария. Список enum-значений не заменяет такую проверку.

## 6. UpdateMenuHook — не место выполнения команды

Комментарий перед `AEGP_RegisterUpdateMenuHook` говорит, что hook вызывается перед показом меню и не относится к одному конкретному меню. Обработчик должен обновить доступность всех относящихся к инструменту пунктов (`AE_GeneralPlug.h:2754–2760`). Callback получает также тип активного окна.

Практическая задача здесь — быстро определить, доступно ли действие сейчас. Не выполнять саму команду, не импортировать файлы и не запускать долгий расчёт вместо обновления интерфейса. Это рекомендация по отзывчивости и предсказуемости, а не запрет, приписанный каждому SDK-вызову.

Easy Cheese в update hook получает текущий active item и проверяет его тип перед EnableCommand (`Easy_Cheese.cpp:62–89`). При переносе идеи нужно явно определить поведение для всех неподходящих состояний, включая пустой проект и переключение контекста. Не следует сохранять когда-то активный item как вечное основание доступности.

**Повторно проверяйте условия при самом выполнении команды.** Состояние могло измениться после update callback; включённый пункт меню не является блокировкой проекта.

## 7. IdleHook и фоновая работа

IdleHook получает `max_sleepPL` в **1/60 секунды**, не в миллисекундах (`AE_GeneralPlug.h:2734–2737`). Это аргумент host callback, не гарантированный таймер с жёстким периодом.

Easy Cheese только увеличивает idle counter (`Easy_Cheese.cpp:47–59`); данный образец не устанавливает частоту callbacks и не показывает производственный файловый watcher.

Для доставки результата из worker-потока SDK содержит специальную функцию `AEGP_CauseIdleRoutinesToBeCalled`. Комментарий `AE_GeneralPlug.h:3008–3013` явно различает:

- сам вызов разрешён из non-main thread;
- вызов асинхронный и возвращается раньше idle handler;
- suite-операции получения этого указателя не thread-safe, поэтому указатель нужно получить в main thread заранее.

Это **узкое разрешение**, не blanket-разрешение использовать AEGP API из любых потоков. Время жизни suite/указателя всё равно должно быть обеспечено владельцем интеграции.

Рекомендуемая архитектура:

```text
worker: только собственные данные/расчёты
    → ограниченная очередь результата
    → запрос idle
host callback: забрать результат, проверить актуальность
    → разрешённые операции с текущим проектом
```

Не держите собственный blocking mutex во время вызова host: скопируйте нужное из очереди, отпустите lock, затем выполняйте host-операции. У каждого результата должна быть проверяемая привязка к запросу/контексту, иначе поздний ответ может примениться уже к другому проекту. Это рекомендации архитектуры; готовая реализация очереди в этой итерации не создаётся.

## 8. Инициализация может завершиться посередине

Рассмотрим ситуацию: state создан, death hook зарегистрирован, пункт меню добавлен, command hook установлен, а update hook не зарегистрировался. Просто удалить ToolState и вернуть ошибку опасно, если host уже хранит callback с этим контекстом.

В просмотренном `AEGP_RegisterSuite5` нет общего unregister-hook API (`AE_GeneralPlug.h:2745–2832`). При этом `AEGP_RemoveMenuCommand` существует в CommandSuite1 (`:2880–2881`). **Удалить пункт, отпустить suite и отменить callback — разные действия.** Отсутствие нужного поля в одной suite не доказывает отсутствие всех механизмов во всём приложении, но не позволяет выдумать rollback для этого примера.

Рекомендуемый подход при проектировании:

1. Сначала выполнить по возможности все проверки и acquisition, которые могут отказать до регистрации.
2. Заранее определить владельца state после первого успешного registration.
3. Отделить состояние «код резидентен, команда выключена» от состояния «инструмент готов».
4. Для каждой точки отказа определить дальнейший lifetime уже переданных host ссылок.

Эта схема требует проверки на целевом host. SDK declarations сами по себе не обещают, что death callback исправит любой crash или любой вариант неудачного initializer.

## 9. Разбор существующего Bible MenuTool

[Исходник MenuTool](../16-WORKING-TEMPLATES/aegp-menu-command/MenuTool.cpp) изучен без изменения реализации. Зафиксированный source snapshot и blob перечислены в [записи сверки](../18-SDK-HEADER-TOOLS/08-REGISTRATION-AEGP-SDK25.6.md). Следующие пункты — **наблюдения по исходному коду, не результаты его запуска**.

### Нормальный путь

Initializer проверяет SPBasicSuite и адрес global refcon, создаёт ToolState через unique_ptr, получает Register/Command/Utility suites. Затем регистрирует DeathHook и передаёт state через global refcon. После этого получает ID, добавляет пункт «Bible Native Tool», регистрирует CommandHook и UpdateMenuHook.

CommandHook отвергает чужую/уже обработанную команду, вызывает DoWork и при успехе отмечает handled. DoWork выводит информационное сообщение. UpdateMenuHook включает собственную команду. DeathHook удаляет ToolState.

Это небольшая демонстрация lifecycle меню. Она не выполняет render, не проверяет пиксели и не подтверждает работоспособность всех AEGP suites.

### Неудачный путь и его границы

До успешной регистрации DeathHook unique_ptr сохраняет владение. После неё владение больше нельзя считать только локальным: указатель возвращён через global refcon. На поздней ошибке код пытается отключить команду, обнуляет её ID в state, сообщает о неудаче и возвращает `A_Err_NONE`, оставляя state для завершения.

**A_Err_NONE в этой ветке не означает, что инструмент полностью инициализирован.** Это выбранная стратегия удержания безопасного контекста и отключения работы. Для диагностического отчёта понадобилось бы отдельное operational status; текущая функция его не возвращает.

Открытые ограничения кода:

- результаты DisableCommand и ReportInfo на error path отбрасываются;
- отсутствует отдельная проверка suppress-interactive-UI перед информационными сообщениями;
- catch-all helper защищает ABI от исключения, но не доказывает успешный rollback после регистрации;
- выключение/обнуление команды не равно удалению всех registrations;
- запуск, частичная регистрация, повторный старт и штатное завершение в целевом AE ещё требуют host evidence.

Ревью не исправляет эти пункты скрытно. Задача Bible — дать читателю точное объяснение существующего кода и не заявлять runtime result без evidence.

## 10. Завершение и режим без интерактивного UI

Для данных, связанных с callback lifecycle, заранее определяют завершающий hook и порядок освобождения. Не следует полагаться только на process-global C++ destructor: он не выражает доступность host API в нужной фазе. Матрица ownership и различающиеся release-контракты разобраны в [главе памяти](../01-ARCHITECTURE/02-MEMORY-THREADING-ERRORS.md).

SDK содержит `AEGP_GetSuppressInteractiveUI`. Его комментарий предупреждает, что попытка модального взаимодействия в режиме без UI может повесить приложение; значение не меняется во время запуска (`AE_GeneralPlug.h:3016–3022`). Поэтому startup/error handling не должны безусловно рассчитывать на диалог.

Практическое правило: перед выбором интерактивного способа сообщения проверяется режим, а для пакетного сценария предусматривается неинтерактивная диагностика. Это отдельная обязанность от успешной регистрации команды. Само наличие пункта меню в обычном AE не подтверждает безопасность другого режима запуска.

## 11. Opaque handles и длинные операции

Не путайте lifetime своего ToolState с lifetime объектов host, на которые он когда-то ссылался. Владение собственным state не делает полученный AEGP handle вечным. Для каждого handle нужны ограничения его конкретной suite, а для выделенного reference — соответствующий release API.

Долгую операцию полезно разделять на проверку актуального контекста, получение необходимых данных, собственную обработку и применение результата в разрешённой фазе. Undo/begin-end, освобождение stream references и правила render receipts изучаются по соответствующим API, а не по одному универсальному destructor.

Эта глава не переносит автоматически правила ScriptUI, Effect-render или Render Queue на AEGP hooks. Подробный цикл проектных операций — тема [следующего раздела](02-PROJECT-RENDER-AUTOMATION.md).

## 12. Как проверить такую интеграцию

Для рабочего AEGP примера нужны раздельные наблюдения: правильный Kind и экспорт, успешный initializer, ровно один пункт меню, реальное выполнение собственной команды, отсутствие перехвата чужих команд, корректная доступность при смене контекста и завершение без потерянного state.

Отдельная матрица отказов включает недоступную suite, ошибку каждой регистрации, исключение после передачи refcon, неинтерактивный режим и запоздалый worker-result. Значения enum и source review не заменяют этих запусков. В данной итерации они **NOT RUN**.

Ключевой вывод: **AEGP — это управление контрактами и временем жизни, а не просто вызов функций по именам.** PiPL определяет описание точки входа; initializer связывает lifetime; hooks получают актуальное событие; suites дают разрешённые операции. Проверять нужно каждый слой отдельно.
