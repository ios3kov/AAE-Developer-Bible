# AEGP: операции с проектом и рендером

Обновлено **2026-10-01**, источник — присланный **SDK 25.6 build 61**. Глава объясняет работу с объектами проекта, очередью и кадрами через AEGP. Она не представляет новый готовый плагин или новый результат рендера.

Ссылки **H:строки** ниже относятся к `Examples/Headers/AE_GeneralPlug.h`, **Old:строки** — к `Examples/Headers/AE_GeneralPlugOld.h`. [Запись сверки](../18-SDK-HEADER-TOOLS/09-AEGP-PROJECT-RENDER-SDK25.6.md) содержит хеши исходников, диапазоны и ограничения. Рекомендации проектирования отделены от объявленного SDK-контракта.

## 1. Сначала определить, какой результат нужен

Операция «отправить композицию на рендер» может означать три разных задачи:

| Задача | Рассматриваемый путь | Что получается |
|---|---|---|
| Подготовить экспорт через очередь AE | RenderQueue + RQItem + OutputModule suites | Элемент очереди с выходными модулями и настройками |
| Прочитать рассчитанный кадр в native-коде | RenderOptions/LayerRenderOptions + Render suite | Receipt и связанный с ним world для чтения |
| Передать отдельно рассчитанное изображение в кэш AE | Timestamp/change checks + CheckinRenderedFrame | Отдельная операция с platform world, не освобождение receipt |

Это разные контракты: H:3199–3502,5131–5443. Наличие API для внешне рассчитанного изображения **не содержит реализации рендера всех эффектов и expressions**. А обычный RenderAndCheckout запрашивает кадр у AE; это не переключение композиции на наш независимый движок.

Как рекомендация выбора технологии: для простой автоматизации сначала оцените сценарный API. AEGP имеет смысл, когда нужная операция уже находится в native-компоненте, требует конкретного suite или связана с его hooks. Сам переход от JSX к C++ не является доказательством ускорения рендера.

AEGP может вызвать сценарий через `AEGP_ExecuteScript`; перед этим есть `AEGP_IsScriptingAvailable`. В объявлении различаются входной текст, выбор кодировки и необязательные result/error handles. Это не прямой вызов произвольной функции JSX как C++-функции. Рекомендация для такого моста: передавать данные с корректным экранированием, отдельно обрабатывать ошибку вызова и возвращённый текст, не склеивать непроверенный ввод с исполняемым кодом. Источник: H:3037–3049; владение memory handles — [глава о памяти](../01-ARCHITECTURE/02-MEMORY-THREADING-ERRORS.md).

## 2. Работа с текущим проектом не требует его переоткрытия

`AEGP_GetNumProjects`, `AEGP_GetProjectByIndex` и `AEGP_GetProjectRootFolder` позволяют начать с уже открытого проекта. Комментарий «всегда один проект» в header прямо помечен AE 5.0; не превращайте историческое замечание в универсальную гарантию новой версии. Код должен проверить результат и наличие нужного проекта. Источник: H:285–307.

Особенно важны два предупреждения:

- `AEGP_NewProject` закрывает открытые проекты.
- `AEGP_OpenProjectFromPath` тоже предупреждает о закрытии открытых проектов.

Это не безопасные вспомогательные вызовы «на всякий случай». Для чтения дерева их не нужно вызывать. `AEGP_ProjectIsDirty` и `AEGP_GetProjectPath` помогают описать текущее состояние; у ещё не сохранённого проекта путь может быть пустым. Проверка dirty flag сама по себе ничего не сохраняет. Источник: H:301–335.

**Рекомендация:** разделить команду чтения, команду изменения текущего проекта и команду открытия другого проекта. Для последней нужен явный сценарий обращения с несохранённой работой. Не вставляйте скрытый Save/New/Open внутрь функции, название которой обещает только получить список объектов.

## 3. Проект, item, comp и layer — не один вид handle

Удобная модель чтения:

```text
Project
  └─ Item: папка / footage / композиция
       └─ Comp: содержимое item-композиции
            └─ Layer
                 ├─ parent comp
                 └─ source item
```

Это схема связей, а не описание порядка обхода SDK. `AEGP_GetCompFromItem` возвращает ошибку для item, который не является композицией; `AEGP_GetItemFromComp` выполняет обратный переход. Layer suite отдельно даёт число слоёв, слой по индексу, его source item и parent comp. Не заменяйте эти вызовы приведением типов. Источники: H:649–660,1005–1043.

Для обхода items используются `AEGP_GetFirstProjItem` и `AEGP_GetNextProjItem`; после последнего next равен NULL. Для восстановления иерархии папок есть `AEGP_GetItemParentFolder`. Из самого First/Next-контракта не следует обещание обхода только непосредственных детей выбранной папки. Active item — отдельное понятие: `AEGP_GetActiveItem` может вернуть NULL. Источник: H:438–448,488–490.

Рекомендуемый read-only проход:

```text
получить и проверить ProjectH
→ получить первый ItemH
→ прочитать тип, ID, имя и parent folder
→ скопировать нужные данные в собственную запись
→ освободить только принадлежащие вызову временные ресурсы
→ получить следующий ItemH
→ закончить на NULL или ошибке
```

Имена и пути требуют внимания к владению. `AEGP_GetItemName` возвращает memory handle с UTF-16; его нужно освободить через `AEGP_FreeMemHandle`. Это не разрешение удалить сам item. `AEGP_DeleteItem` удаляет проектный объект и убирает его из композиций. Освобождение строки и удаление объекта — принципиально разные действия. Источник: H:467–478,514–520.

### Индекс, ID и живой handle

Индекс удобен для обхода текущего списка. Для item существует `AEGP_GetItemID`; для layer — `AEGP_GetLayerID` и поиск `AEGP_GetLayerFromLayerID(parent_compH, id, ...)`. Последний требует parent comp: один сохранённый номер слоя ещё не описывает весь контекст поиска. Источники: H:476–478,1177–1179,1211–1214.

Рекомендация для долгой операции: хранить собственный снимок с контекстом проекта/композиции и ID, а перед изменением заново разрешать цель и проверять её. При удалении, смене проекта или неоднозначном разрешении отменять соответствующее действие, а не выбирать объект с похожим именем. Указанные объявления не устанавливают универсальную долговечность ID после закрытия проекта, импорта и объединения файлов — такую гарантию здесь не заявляем.

## 4. Время нужно передавать вместе с его смыслом

`A_Time` содержит `value` и `scale` (`Examples/Headers/A.h:88–91`). Для собственного расчёта времени сохраняйте рациональную пару, не только округлённую строку секунд. Например, математически 12 кадров при 24 кадрах/с дают `12/24 = 0,5` секунды. Это пример арифметики, не измерение квантования AE.

Кроме численного значения важно временное пространство. `AEGP_GetItemDuration` и `AEGP_GetItemCurrentTime` используют native timespace item; комментарий ко второму отдельно предупреждает, что время **не обновляется во время рендера**. Поэтому положение курсора item нельзя выдавать за время каждого рассчитываемого кадра. Источник: H:496–503.

Для перехода между comp time и layer time существуют `AEGP_ConvertCompToLayerTime` и `AEGP_ConvertLayerToCompTime`. Когда операция требует такого перехода, используйте её контракт вместо универсальной самодельной формулы вычитания начала слоя. Источник: H:1162–1170.

В render options `SetTime` задаёт момент кадра, а `SetTimeStep` — его длительность; header отмечает значение time step для motion blur. Это не две записи одного параметра. В отчёте воспроизведения нужны обе пары value/scale. Источник: H:5150–5164.

## 5. Изменение проекта: Undo не является автоматическим rollback

`AEGP_StartUndoGroup` должен быть сбалансирован `AEGP_EndUndoGroup`. Но эти объявления не обещают транзакционного отката: ошибка третьей операции не означает, что первые две исчезли. У конкретных операций отдельные пометки UNDOABLE; например, они присутствуют у SetItemName и DeleteItem. Источники: H:472–474,514–515,2955–2958.

Рекомендуемый порядок для пакетного изменения:

```text
проверить цель и входные данные без изменений
→ подготовить план и исходные значения
→ начать Undo group
→ выполнять изменения, проверяя каждый результат
→ прочитать изменённые значения обратно
→ закончить Undo group и сохранить его ошибку отдельно
→ сообщить фактически выполненную часть
```

Если требуется rollback, его нужно проектировать отдельно: какие операции обратимы, какие объекты создала именно эта команда, что делать после частичной ошибки. Не называйте произвольный вызов Undo из плагина универсальным исправлением состояния.

`StartQuietErrors`/`EndQuietErrors` решают другую задачу — режим сообщения об ошибках. Они не делают упавшую операцию успешной и не заменяют обработку возвращённого `A_Err`. Комментарий к EndQuietErrors говорит о последней подавленной ошибке, а не полном журнале всех ошибок. Источник: H:2943–2953.

Расчёт собственного плана можно отделить от вызовов host. Но существование worker-потока не разрешает перенести на него любые suites. У `CauseIdleRoutinesToBeCalled` есть специальное non-main разрешение, а получение этого указателя через suites прямо исключено из него. Используйте разрешённый контекст вызова, разобранный в [главе hooks](01-HOOKS-SUITES.md). Источник: H:3008–3022.

## 6. Получить кадр: сначала выбрать границу изображения

`RenderOptionsSuite4::AEGP_NewFromItem` создаёт options с временем 0 и time step, равным длительности кадра. `LayerRenderOptionsSuite2::AEGP_NewFromLayer` описан иначе: текущее время слоя, его frame duration, nominal bounds и все эффекты. Поэтому одинаковое слово New не означает одинаковые исходные настройки. Источник: H:5131–5149,5243–5257.

Для layer options дополнительно есть:

| Конструктор | Заданная источником граница |
|---|---|
| `AEGP_NewFromLayer` | Layer с EffectsToRender, установленным в all |
| `AEGP_NewFromUpstreamOfEffect` | Граница перед указанным эффектом |
| `AEGP_NewFromDownstreamOfEffect` | Включает результат указанного эффекта; создание разрешено только из UI thread |

Источник: H:5247–5272. Это не автоматическое равенство с финальным кадром композиции или файлом output module. При сравнении данных фиксируйте, какая именно граница выбрана.

Для item options отдельно задаются и читаются обратно время, time step, field mode, world type, downsample, ROI, matte mode и порядок каналов. `SetRenderGuideLayers` тоже существует отдельно. Настройка render quality в этом suite описана для footage; её нельзя без основания назвать универсальным quality-переключателем всей композиции. Источник: H:5150–5240.

**Особый случай ROI:** у `AEGP_SetRegionOfInterest` прямоугольник `{0,0,0,0}` означает всю область. Он не является здесь запросом пустого результата. Не переносите значение sentinel из другой API-группы. Источник: H:5197–5199.

## 7. Receipt владеет доступом к кадру, world только заимствован

Последовательность синхронного чтения через Render suite:

```text
создать и настроить options
→ RenderAndCheckoutFrame / RenderAndCheckoutLayerFrame
→ проверить ошибку и полученный receipt
→ GetReceiptWorld и GetRenderedRegion
→ прочитать world, не изменяя его
→ CheckinFrame
→ Dispose собственных options
```

`AEGP_GetReceiptWorld` возвращает **read-only world, не принадлежащий плагину**. Освобождение доступа выполняется через `AEGP_CheckinFrame`, а не `WorldSuite::Dispose` для этого world. Пиксельный указатель нельзя сохранять для использования после checkin. Источник: H:5356–5395.

У WorldSuite3 есть `AEGP_GetType`, `AEGP_GetSize`, `AEGP_GetRowBytes`, `AEGP_GetBaseAddr8/16/32`. Typed base-address функции документируют ошибку при несовпадении типа. Не выбирайте интерпретацию памяти только по настройке проекта или имени файла; проверьте возвращённый world. `AEGP_FastBlur` в этом suite отдельно запрещён для checked-out read-only frames: он предназначен для user-allocated worlds. Источник: H:5026–5084.

Если данные нужны позже собственному worker, рекомендация — скопировать нужные строки в принадлежащий приложению буфер, пока receipt ещё действителен. Вместе с байтами сохранить размер, stride копии, тип, область, время и выбранную модель alpha. Как обращаться с пикселями, разобрано в [главе цвета](../02-EFFECT-PLUGINS/06-COLOR-PIXELS.md). Копия не превращает raw world в готовый PNG/PSD: для файла существует отдельный путь экспорта.

Cleanup должен выполняться и при ошибке потребителя. При этом полезно сохранять отдельно основную ошибку и ошибку checkin: иначе успешный consumer скроет неудачное освобождение, либо cleanup затрёт исходную причину. Это рекомендация построения адаптера; [глава памяти](../01-ARCHITECTURE/02-MEMORY-THREADING-ERRORS.md) показывает различные семейства release API.

### Синхронный вызов не следует ставить в каждую перерисовку UI

В RenderSuite5 header считает синхронный рендер на UI thread устаревшей моделью, кроме узкого случая: пользователь явно запросил операцию, которой кадр нужен для изменения database. Это не общий запрет sync-render, но и не разрешение блокировать UI при каждом refresh. Указаны async-альтернатива и автоматическое окно progress для долгого sync-вызова на UI thread. Источник: H:5346–5371.

Async-вариант рассматриваемого suite относится к layer frame: `AEGP_RenderAndCheckoutLayerFrame_Async` возвращает request ID, callback получает ID, признак отмены, ошибку и receipt при успехе. `AEGP_CancelAsyncRequest` — отдельная операция. Callback обещан с исключением при shutdown AE. Из этого объявления нельзя вывести, что после отмены можно немедленно уничтожить refcon, или что при shutdown callback обязательно придёт. Проектируйте lifetime запроса и shutdown отдельно; поток выполнения callback здесь не угадывается. Источник: H:5333–5344,5373–5380.

## 8. Очередь: разные состояния и два уровня invalidation

Состояние **очереди** — STOPPED, PAUSED или RENDERING. Состояние **элемента** — например NEEDS_OUTPUT, UNQUEUED, QUEUED, USER_STOPPED, ERR_STOPPED или DONE. Это разные enum и разные setters. В RenderQueueSuite1 отдельно запрещён переход STOPPED → PAUSED. Источник: H:3199–3239.

`AEGP_SetRenderState` элемента требует STOPPED у всей очереди; неподходящий статус или отсутствие необходимого output path может дать ошибку. Не исправляйте это скрытой остановкой пользовательского рендера. Рекомендация безопасной команды — сообщить, что редактирование очереди сейчас недоступно. Источник: H:3338–3348; для старой RQItemSuite3 тот же контракт есть в Old:198–208.

**Не кэшируйте refs очереди:**

| Что изменилось | Что header объявляет недействительным |
|---|---|
| Состав или порядок render items | Все `AEGP_RQItemRefH` |
| Состав или порядок output modules элемента | Все `AEGP_OutputModuleRefH` в указанном контракте |

Источники: H:3317–3324,3393–3401. После таких операций заново получите нужные refs. Сохранённый номер индекса тоже требует проверки цели: после перестановки на том же месте может находиться другой элемент. Последнее — рекомендация выбора цели, не расширение SDK-гарантии.

`AEGP_AddCompToRenderQueue` принимает comp и `const A_char*` path, но не возвращает новый RQItemRefH. `AEGP_SetOutputFilePath` принимает UTF-16 путь. Это различие объявлений, не повод кастовать один указатель к другому. Для собственных путей нужна корректная конверсия и отдельное тестирование Unicode на целевой платформе. Источники: H:3227–3230,3480–3488.

## 9. Подготовка экспорта должна завершаться чтением настроек обратно

Рекомендуемый сценарий для команды, которая только готовит **свой** элемент:

```text
проверить STOPPED, comp и допустимый выходной путь
→ добавить элемент
→ заново определить добавленную цель, без старых refs
→ получить её output module
→ настроить путь и необходимые параметры
→ прочитать обратно путь, channels, crop/stretch и post-render action
→ выставить QUEUED именованной константой
→ прочитать состояние элемента
```

Если после Add произошла ошибка, в очереди уже может остаться созданный элемент. Функция должна сообщить об этом или выполнить заранее определённый rollback только своей операции. Формат «вернули ошибку, значит ничего не изменилось» неверен для такого сценария.

Для output module есть отдельные настройки enabled video/audio, RGB/RGBA/alpha, crop, stretch и post-render actions. Среди actions есть импорт, замена usage и установка proxy. Поэтому экспорт может иметь побочные изменения проекта; проверяйте их, а не только путь. `AEGP_GetExtraOutputModuleInfo` возвращает сведения о формате и признаки sequence/multi-frame. Название с расширением `.png` не заменяет эти настройки. Источник: H:3263–3307,3413–3500.

Подготовка своего элемента и **запуск общей очереди** должны быть разными решениями. Setter состояния очереди не принимает handle только одного нашего элемента. Перед запуском нужно учитывать другие queued items и явное намерение пользователя. Не отправляйте чужие элементы на рендер как побочный эффект preview-команды.

### Ошибка, которая компилируется: TRUE вместо статуса

В более ранней версии [RenderQueueRecipes.cpp](../17-NATIVE-SUITE-COOKBOOK/code/RenderQueueRecipes.cpp) последний вызов передавал `TRUE` в `AEGP_SetRenderState`. Но аргумент — `AEGP_RenderItemStatusType`, не `A_Boolean`. При обычном TRUE=1 это **UNQUEUED**, тогда как QUEUED равен 2. Источники: H:3210–3225; Old:206–208; `SPTypes.h:60–61`. Текущий рецепт исправлен на именованный `AEGP_RenderItemStatus_QUEUED` и проверяет результат через `AEGP_GetRenderState`.

Иллюстрация нужного выбора enum для уже проверенных suite/ref:

```cpp
A_Err err = rq_items->AEGP_SetRenderState(
    rq_item, AEGP_RenderItemStatus_QUEUED);

AEGP_RenderItemStatusType actual = AEGP_RenderItemStatus_NONE;
if (!err) {
    err = rq_items->AEGP_GetRenderState(rq_item, &actual);
}
// Успех операции постановки требует также actual == AEGP_RenderItemStatus_QUEUED.
```

Это фрагмент контракта, не законченный плагин. Текущий cookbook-рецепт теперь применяет тот же named-enum + readback pattern. Это закрывает исходную ошибку выбора аргумента, но не заменяет host test: состояние общей очереди, output configuration, invalidation и реальный запуск должны проверяться внутри AE.

Запись с TRUE встречается и в QueueBert:131. Рядом sample использует нулевые/числовые refs и фиксированный путь, а Projector:670–703 добавляет несколько элементов и содержит старт рендера в закомментированном блоке. Читайте samples как конкретный исходник с историческими особенностями, а не как готовый безопасный installer/automation pipeline.

## 10. Кэш: два разных checkin и защита от устаревшего результата

`AEGP_CheckinFrame(receipt)` возвращает доступ к взятому кадру. `AEGP_CheckinRenderedFrame(options, timestamp, ticks, platform_world)` передаёт отдельно подготовленное изображение; аргумент image помечен adopted. Сходство названий не делает их взаимозаменяемыми release-функциями. Источник: H:5382–5391,5435–5440.

Для speculative rendering header описывает проверки полезности до отправки задания и после его завершения, а также `AEGP_HasItemChangedSinceTimestamp`. Этот change check относится к видео и не учитывает аудио. Timestamp увеличивается при затрагивающих рендер изменениях, поэтому его не следует переименовывать в номер кадра. Источник: H:5413–5433.

Рекомендация: вычисленный результат несёт снимок запроса — объект, время, options и timestamp. Перед публикацией нужно проверить, всё ли ещё относится к текущей задаче. При этом описанный механизм не удостоверяет правильность пикселей стороннего движка и не снимает необходимость алгоритмического сравнения.

## 12. Как проверять будущую реализацию

Это **план проверки**, не результаты новой серии запусков. Для read-only команды проверяются пустой/несохранённый проект, отсутствие active item, папки, Unicode и отсутствие изменений. Для mutation — успешное действие, Undo, смена цели и частичная ошибка. Для очереди — занятая очередь, несколько чужих items, несколько output modules, invalidation, проверка enum и пути. Для кадров — известное время, граница upstream/downstream, 8/16/32-bit world, фактическая область, alpha, отмена и release. Для async — устаревшие запросы и завершение приложения.

Статус DONE у очереди — отдельное наблюдение. Для приёмки экспорта дополнительно нужны реальные файлы с проверенными форматом, количеством кадров, размером и содержимым. Ранее исследованный [случай 3D Channel Extract](../21-BUILTIN-EFFECTS-REVERSE-ENGINEERING/3D-Channel/3D-Channel-Extract/EVIDENCE-AUDIT-2026-09-30.md) показывает, почему отчёт коллектора нельзя автоматически считать полной проверкой пикселей.

Эта глава завершает редакционное объяснение рассмотренных контрактов. Она не закрывает native build, host execution, исправление отмеченного queue-рецепта или остальные gates [согласованного плана](../COMPLETION-CHECKLIST.md).
