# MFR: параллельный рендер, состояние и Compute Cache

Основа: присланный **After Effects SDK 25.6 build 61**. Сверка: **2026-10-01**. Все пути источников ниже относительны `Examples/`; SHA-256 и ограничения — в [обзоре памяти и MFR](../18-SDK-HEADER-TOOLS/07-MEMORY-MFR-SDK25.6.md).

Глава объясняет, какие обещания даёт плагин при включении threaded rendering. Это не отчёт об ускорении, запуске MFR или готовности наших эталонных примеров. Контракты SDK отделены от рекомендаций по устройству собственного эффекта.

## 1. Флаг не распараллеливает небезопасный код

`PF_OutFlag2_SUPPORTS_THREADED_RENDERING` означает, что effect допускает одновременные render-вызовы на нескольких потоках. В описании явно упомянуты одно и несколько применений эффекта на слое. Следовательно, защита только от второго экземпляра эффекта недостаточна: нужно учитывать параллельную работу над одним эффектом.

Источник: `Headers/AE_Effect.h:912–918`.

В этой поставке актуальный флаг имеет значение `1L << 27` и относится к `GLOBAL_SETUP`. Старые `PF_OutFlag2_I_AM_THREADSAFE` и `PF_OutFlag2_AE13_5_THREADSAFE` помечены как unused. Их похожие названия не делают их заменой текущего threaded-rendering флага.

Источник: `Headers/AE_Effect.h:984–1010`.

**Рекомендация Библии:** сначала спроектировать владение и доступ к состоянию, затем проверять конкурентное выполнение, и только после этого включать capability в поставляемой сборке. Внутренняя тестовая сборка с флагом нужна для самих MFR-тестов; она не становится release-ready только из-за наличия флага.

## 2. Какие команды могут пересекаться

В комментарии флага зафиксированы следующие границы:

| Область | Что говорит эта поставка |
|---|---|
| UI selectors | Остаются на main thread |
| Sequence setup/resetup/setdown, pre-render и render | Общее описание MFR предупреждает о возможном выполнении на нескольких потоках одновременно с UI selectors |
| Global setup/setdown | Остаются на main thread и не отправляются одновременно с другими selectors, независимо от этого флага |

Источник: `Headers/AE_Effect.h:912–921`.

**Не скрывать различие комментариев.** Описание `SEQUENCE_SETUP` в `:1084–1092` говорит об UI thread с оговоркой для legacy effects. Описание `GET_FLATTENED_SEQUENCE_DATA` в `:1115–1125` отдельно гарантирует UI-only sequence setup при его поддержке, но допускает resetup на UI или render thread. Это более узкие условия рядом с общей MFR-формулировкой; глава не превращает их в безусловное обещание «весь sequence lifecycle однопоточный». Точная последовательность конкретного плагина требует отдельного host-теста.

Отсюда важная архитектурная задача: UI не должен менять тот же рабочий массив, из которого параллельно читает render. Сам факт нахождения UI на main thread не синхронизирует его с render-потоками.

## 3. Один кадр тоже может обрабатываться несколькими потоками

MFR — не единственный источник параллельности. Комментарий `PF_ITERATE` разрешает host распределять iteration между потоками. Данные за `refcon` должны быть read-only либо корректно синхронизированы. Это правило действует на уровне pixel callbacks и не исчезает от того, что тестируется только один кадр.

Источник: `Headers/AE_EffectCB.h:687–694`.

**Рекомендуемое разделение:**

```text
UI / параметры
    → самостоятельный согласованный snapshot
        → один render-запрос: свои временные buffers
            → pixel callbacks: неизменяемый refcon,
              запись только в назначенные элементы output
```

Это схема проектирования, не схема гарантированного планировщика AE. В ней нет общего `current_time`, изменяемого всеми вызовами, и нет требования, чтобы кадр N был закончен раньше N+1.

## 4. Read-only sequence data во время threaded render

Для эффекта с `SUPPORTS_THREADED_RENDERING` header указывает:

- sequence data во время render доступно только для чтения;
- читать его нужно через `PF_EffectSequenceDataSuite`;
- `in_data->sequence_data` во время render будет `NULL`;
- для изменяемого render-кэша предлагается Compute Cache, а не запись в обычное sequence state.

Источник: `Headers/AE_Effect.h:923–930`.

Точная декларация находится в **`AE_GeneralPlug.h`**, а не определяется по названию главы: `PF_EffectSequenceDataSuite1` предоставляет `PF_GetConstSequenceData`. Результат имеет тип `PF_ConstHandle`; соответствующие typedef сохраняют const на указателях. В этой таблице нет отдельного `CheckinConstSequenceData`.

Источник: `Headers/AE_GeneralPlug.h:5707–5718`.

**Рекомендация использования:** проверить acquisition suite и результат вызова; считать полученные данные заимствованными и read-only; не снимать `const`, не освобождать их собственным deleter и не превращать их адрес в долговечный кэш. Отсутствие пары checkin в этой таблице не означает, что возвращённый адрес принадлежит плагину. В просмотренной декларации не задан универсальный срок хранения такого адреса между командами — это не следует придумывать.

Если sequence state содержит вложенные указатели, const верхнего handle сам по себе не доказывает, что вложенное содержимое безопасно для конкурентного доступа. Конкретная модель вложенных объектов остаётся обязанностью реализации.

## 5. Flattening обязателен не для любого эффекта, а по условию

Когда одновременно нужны threaded rendering и `PF_OutFlag_SEQUENCE_DATA_NEEDS_FLATTENING`, SDK требует также `PF_OutFlag2_SUPPORTS_GET_FLATTENED_SEQUENCE_DATA`. Последний selector возвращает независимую сериализованную копию и передаёт владение ею host. Он отличается от исторического `SEQUENCE_FLATTEN`, заменяющего рабочее состояние.

Источники: `Headers/AE_Effect.h:923–924,1005,1104–1138`.

Это не означает, что каждому stateless-эффекту следует добавить sequence allocation. **Рекомендация:** не создавать состояние только ради соблюдения воображаемого MFR-шаблона. Если оно необходимо, разделить сериализуемые пользовательские данные и восстановимые временные объекты. Разбор двух вариантов flattening на PathMaster — в [главе о памяти](../01-ARCHITECTURE/02-MEMORY-THREADING-ERRORS.md).

Сам PathMaster выставляет threaded-rendering и get-flattened flags (`Effect/PathMaster/PathMaster.cpp:80–84`). Это факт его исходника, а не результат нашего concurrency-теста и не свидетельство готовности всех примеров SDK.

## 6. `MUTABLE_RENDER_SEQUENCE_DATA_SLOWER` — не общая изменяемая память

Флаг `PF_OutFlag2_MUTABLE_RENDER_SEQUENCE_DATA_SLOWER` описан как запрос репликации sequence data **для каждого render thread**, чтобы поток мог изменять свою копию. Изменения регулярно отбрасываются; header приводит текущие примеры границ — окончание RAM Preview или Render Queue export.

Источник: `Headers/AE_Effect.h:932–935`.

Из этого нельзя делать постоянное хранилище пользовательских изменений. Копия на render thread не равна новой копии для каждого кадра; её содержимое также нельзя считать согласованным с копиями других потоков.

**Рекомендация Библии:** рассматривать этот путь как отдельный компромисс, когда read-only state и Compute Cache не подходят. Проверять затраты памяти и сохранение корректности при пересоздании копий. Не использовать его для связи «следующий кадр прочитает результат предыдущего» и не включать безусловно во все эффекты.

Название флага предупреждает о возможной цене, но не даёт численного прогноза замедления для нашего алгоритма. Такой прогноз требует замера.

## 7. Compute Cache: значение принадлежит кэшу, доступ оформляется receipt

`AEGP_ComputeCacheSuite1` в поставке использует строку имени `AEGP Compute Cache`, версию 1. Плагин регистрирует глобально уникальный идентификатор класса вычисления и таблицу callbacks.

Источники: `Headers/AE_ComputeCacheSuite.h:34–49,82–95`.

| Callback | Назначение из SDK |
|---|---|
| `generate_key` | Быстро получить ключ, включающий все входы, необходимые для однозначной идентификации вычисления |
| `compute` | Построить вычисленное значение |
| `approx_size_value` | Сообщить полный примерный объём памяти значения; размер участвует в выборе того, что удалять из кэша |
| `delete_compute_value` | Освободить все ресурсы, которыми владеет удаляемое значение |

Источник: `Headers/AE_ComputeCacheSuite.h:54–78`.

Значение может быть неплоским. Значит, если оно владеет несколькими массивами, стоимость нельзя автоматически сводить к `sizeof` верхнего объекта. Его очистка также должна учитывать вложенные ресурсы. Это следствие описания callbacks, а не требование использовать определённый C++ контейнер.

Основная последовательность доступа:

```text
зарегистрированный compute class + options
    → ComputeIfNeededAndCheckout
    → получить receipt при успехе
    → GetReceiptComputeValue
    → использовать значение в пределах полученного доступа
    → CheckinComputeReceipt до возврата host
```

Источники: `Headers/AE_ComputeCacheSuite.h:98–167`.

Получить cache value и владеть им — разные действия. Удаление самого значения происходит через зарегистрированный `delete_compute_value`. `AEGP_ClassUnregister` очищает значения этого класса: после unregister callback удаления больше недоступен.

Источники: `Headers/AE_ComputeCacheSuite.h:74–77,92–95`.

**Рекомендация:** не хранить в значении borrowed pixel pointer после окончания его checkout. Либо значение владеет самостоятельной копией нужных данных, либо хранит вычисленный результат без такой зависимости. Cache receipt не продлевает автоматически другие, независимо полученные ресурсы.

## 8. Не путать «не ждать другой поток» с «ничего не вычислять»

У `AEGP_ComputeIfNeededAndCheckout` аргумент `wait_for_other_threadB` управляет ожиданием **уже начавшегося вычисления другого потока**.

| Состояние записи | `false` | `true` |
|---|---|---|
| Значения нет и его ещё не вычисляют | Вычислить и выдать checkout | Вычислить и выдать checkout |
| Другой поток вычисляет значение | Вернуть `A_Err_NOT_IN_CACHE_OR_COMPUTE_PENDING` | Дождаться и выдать checkout |
| Значение уже готово | Выдать checkout | Выдать checkout |

Источник: `Headers/AE_ComputeCacheSuite.h:104–141`.

Поэтому `false` **не является универсальным неблокирующим режимом**: собственное `compute` всё ещё может быть дорогим. Для запроса только уже готового значения есть `AEGP_CheckoutCached`: комментарий прямо исключает вычисление и ожидание другого потока. При промахе он возвращает `A_Err_NOT_IN_CACHE_OR_COMPUTE_PENDING`; при успехе receipt также обязательно вернуть.

Источник: `Headers/AE_ComputeCacheSuite.h:148–158`.

Header описывает multi-checkout pattern: сначала запросить несколько зависимостей без ожидания чужого вычисления, затем повторить с ожиданием те, для которых пришёл pending. Но схема в комментарии `:112–125` — **не готовый C++ образец**: в ней переменные ошибок названы `bool`, тогда как реальные функции возвращают `A_Err`. В собственной реализации нужно сохранять полный код, иначе сравнение с конкретным pending-кодом теряет смысл. Это разбор текста header, не новый runtime-дефект AE.

Не нужно возвращать receipt после failed checkout, который его не выдал. Но если receipt получен, ошибка последующей обработки не отменяет обязательного checkin. Подробнее — [cleanup после ошибки](../01-ARCHITECTURE/02-MEMORY-THREADING-ERRORS.md).

## 9. Правильный ключ не менее важен, чем mutex

В комментарии `generate_key` требуется включать все входы вычисления. Если для значения нужен layer checkout, следует учитывать состояние этого входа. В качестве механизма указан `PF_GetCurrentState`; header отдельно поясняет, что речь о хэше зависимостей для получения кадра, **не о хэше уже отрендеренных пикселей**. Сам такой запрос состояния не запускает render.

Источник: `Headers/AE_ComputeCacheSuite.h:54–59`.

**Рекомендация:** включать время, настройки алгоритма, режим качества, размеры, pixel depth и внешнее состояние ровно тогда, когда они меняют конкретное кешируемое значение. Например, таблице, зависящей только от радиуса, не нужен идентификатор каждого кадра. Но результат анализа изображения нельзя идентифицировать одним размером кадра, если содержимое меняется.

Не следует путать Compute Cache key с идентичностью финального кадра у AE. Для Smart effects с `PF_OutFlag2_I_MIX_GUID_DEPENDENCIES` header отдельно описывает `GuidMixInPtr`: состояние, влияющее на render и не представленное обычным AE stream parameter, должно учитываться в GUID кадра. Состояние, не влияющее на результат, добавлять не рекомендуется, чтобы не портить использование кэша.

Источник: `Headers/AE_Effect.h:899–910`.

Следствие для проекта: потокобезопасный кэш с неполным ключом всё равно способен возвращать устаревший результат. Защита памяти и правильность зависимостей — разные проверки.

## 10. Карта состояния перед включением MFR

Следующая таблица — **рекомендация Библии**, а не список новых SDK-типов.

| Данные эффекта | Предпочтительное место/модель | Что проверить |
|---|---|---|
| Неизменяемая таблица алгоритма | Общее состояние, инициализированное до использования | Нет скрытой ленивой записи во время render |
| Значения параметров для запроса | Согласованный snapshot | Нет указателей на изменяемый UI-объект |
| Scratch buffer кадра | Локальный владелец render-запроса | Не разделяется с другим запросом |
| Дорогой повторяемый результат | Кэш с полным ключом и ограниченным временем владения | Cleanup, память, совпадающие и разные ключи |
| Временное mutable sequence state | Только по документированному отдельному механизму | Потеря копии не меняет алгоритмический результат |
| Сторонняя библиотека | Проверенная модель её собственного контекста | Нет общего небезопасного singleton или скрытой записи |

Для MFR [public guide прямо запрещает](https://github.com/docsforadobe/after-effects-plugin-guide/blob/6d9b285d9755d1fbf8ead7680ba49de24f94b547/docs/effect-details/multi-frame-rendering-in-ae.md#L105-L116)
удерживать blocking mutex/gate при вызове host, включая suites и checkout.
Это DOCUMENTED-ограничение данного MFR-контекста; оно не выводится из одного лишь
наличия `const` или RAII. Общая осторожная рекомендация для остальных API-семей
остаётся в главе о памяти. В SDK есть явный пример риска: layer checkout из `UPDATE_PARAMS_UI` возвращает чёрные pixels для предотвращения render-запроса и возможного deadlock (`Headers/AE_Effect.h:2661–2667`).

Обновление UI и вычисление изображения следует разделять; готовое значение для UI можно читать по подходящему контракту, но UI callback не становится render thread только потому, что там вызвана suite-функция.

## 11. Проверка MFR: критерии, а не новый тестовый продукт

Ниже — **рекомендуемая матрица для последующей проверки примеров**, не выполненные в этой итерации прогоны.

| Проверка | Какой риск ищем |
|---|---|
| Один кадр, повторный запрос, совпадающие параметры | Нестабильный локальный state |
| Разный порядок кадров и разные времена | Скрытая зависимость от «предыдущего кадра» |
| Несколько применений/экземпляров | Общее изменяемое состояние |
| UI-изменения параллельно обработке | Несогласованный snapshot |
| Одинаковые и разные cache keys | Неверное совместное использование результата |
| Ошибка compute, отмена, ошибка после receipt | Пропущенный checkin и зависшее ожидание |
| Resetup, дублирование, save/reopen, setdown | Ошибка восстановления и срока жизни |
| Контролируемое сравнение последовательного и MFR output | Изменение пикселей из-за конкурентного выполнения |

Для сравнения фиксируют одинаковые входы, время, render/output settings, точность хранения и допустимое расхождение. Успех Render Queue подтверждает завершение задания, но не равен доказательству конкурентного выполнения именно нашего эффекта. Для такого вывода нужны наблюдаемые данные о вызовах и их пересечении, а не только включённый флаг или настройка проекта.

Память следует оценивать вместе с параллельностью. Как расчётная модель, не замер AE: если одному запросу нужно S байт scratch, то N одновременно активным запросам может потребоваться примерно N×S плюс общие данные. Глобальный mutex способен сделать обработку безопаснее, но ограничить её масштабирование; измерять нужно и корректность, и пиковую память, и время.

## 12. Walkthrough: таблица resampling в Compute Cache

Design example: cache value содержит immutable indices/weights для осевого
mapping, но не input pixels. Key сериализует algorithm/schema version, source/output
dimensions, mapping coefficients, kernel и boundary mode в canonical fields без
padding. Time/content hash нужен только если **эта таблица** зависит от времени
или изображения; не добавлять frame identity в чисто геометрическую таблицу.

```text
ClassRegister at allowed lifecycle → options/key
→ ComputeIfNeededAndCheckout
    pending without receipt → chosen retry/fallback policy
    error without receipt → return primary error
    success + receipt → GetReceiptComputeValue
        success → use borrowed immutable table
        error/cancel → no further reads
    → CheckinComputeReceipt (also on error)
→ return primary error; report checkin error separately
ClassUnregister only after outstanding work is quiescent
```

Compute allocates candidate locally, validates bounds/overflow/memory budget and
publishes only complete value. `approx_size_value` включает все arrays; delete callback
освобождает только собственные arrays. Receipt хранится в request scope; cache
value не delete-ится consumer. Нельзя unregister class, пока code/value используются;
shutdown запрещает новую работу до teardown. Call-local intermediate Bicubic rows
остаются request scratch, не mutable cache value. Exceptional mapping использует
исходный fallback без изменения arithmetic.

Recommendation для failure injection: fail до receipt, после receipt, после value,
в compute allocation и при cancellation. Считать acquisitions/checkins и peak memory
отдельно от output equality. Наличие mutex не исправляет неполный key; отсутствие
MFR flag не делает iterate callback однопоточным.

### Cache может исчезнуть; thread-local не равен request-local

**DOCUMENTED / RUNTIME-NOT-CLAIMED, review 2026-10-08.**
Compute Cache не сохраняется в project и может быть вытеснен из-за памяти.
Корректный эффект способен снова выполнить compute при следующем запросе;
доступность cache не должна определять пользовательский результат.
[Persistence](https://github.com/docsforadobe/after-effects-plugin-guide/blob/6d9b285d9755d1fbf8ead7680ba49de24f94b547/docs/effect-details/compute-cache-api.md#L255-L269).
Options должны содержать все входы, нужные и generate_key, и compute. Хешировать
каноническое содержимое, а не адрес: `sizeof(const char*)` из guide sample не
является длиной строки. Сам sample имеет незавершённый return/error path и не
служит готовым callback.

`thread_local` разделяет потоки, но не экземпляры эффекта и не повторный вход
на одном потоке. Это вывод для архитектуры: хранить frame-specific scratch в
request scope. По MFR guide запись в `global_data` во время render запрещена;
`UPDATE_PARAMS_UI` также не является местом изменения sequence render state.
Сканер static/global symbols полезен как inventory, но отсутствие находок не
доказывает корректности сторонней библиотеки или cache key.
[MFR guidance](https://github.com/docsforadobe/after-effects-plugin-guide/blob/6d9b285d9755d1fbf8ead7680ba49de24f94b547/docs/effect-details/multi-frame-rendering-in-ae.md#L105-L202).

Исходная сверка проверяла **декларации и комментарии SDK25.6 build61**. Дополнения от 2026-10-08 основаны на отдельно указанном public guide и не являются новым exact-header review. MFR stress, измерение ускорения, проверка конкретного GPU, native-компиляция новой реализации и её загрузка в AE здесь не заявлены. Такие результаты не выводятся из успешной сборки документации.
