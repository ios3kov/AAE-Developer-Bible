# Дополнительные каналы: глубина, ID, нормали и сырые данные (Auxiliary Channels)

**Основа:** заголовки из присланного SDK 25.6 build 61. Это глава о публичном контракте данных, не новый collector и не протокол запуска эксперимента. [Идентичность SDK](../18-SDK-HEADER-TOOLS/05-SUPPLIED-SDK-25.6.md).

Главное различие: RGBA изображения и auxiliary-данные источника — не одно и то же. Серое изображение может визуализировать глубину, но наличие серых пикселей само по себе не означает, что источник предоставляет канал `DPTH`. В SDK получение auxiliary-описаний и buffers оформлено отдельным `PF_ChannelSuite1`. [C1], [C2]

## Источники

| Метка | Файл и строки внутри SDK | Предмет |
|---|---|---|
| C1 | `Examples/Headers/AE_Effect.h:1441–1548` | Семантика канала, тип компонента, descriptor, reference и chunk |
| C2 | `Examples/Headers/AE_ChannelSuites.h:49–94,521–561` | Запросы, время, выделение и обязательный checkin |
| C3 | `Examples/Headers/AE_ChannelSuites.h:103–216,231–243` | Макросы доступа и пример адресации строки |
| C4 | `Examples/Headers/AE_Effect.h:2576–2583` | Отличающееся время жизни SmartFX image world |

## 1. Путь данных

```text
Источник слоя
  → предоставленные AE auxiliary-описания
  → lookup по индексу или типу канала
  → PF_CheckoutLayerChannel
  → PF_ChannelChunk: тип + размеры + stride + dataPV
  → ваша обработка
  → PF_CheckinLayerChannel
```

Это логическая схема из [C1–C2]. Она не утверждает, что любой импортёр или любой слой предоставляет все перечисленные SDK-типы. Заголовок описывает язык интерфейса, а не содержимое конкретного RPF, RLA, EXR или прекомпозиции.

Для проекта `3D Channel Extract` это принципиально: наши прежние измерения на вложенной композиции сохраняются как [наблюдения Z-Depth](../21-BUILTIN-EFFECTS-REVERSE-ENGINEERING/3D-Channel/3D-Channel-Extract/EVIDENCE-AUDIT-2026-09-30.md), а не автоматически становятся проверкой импортированных ID/UV/нормалей.

## 2. Семантика, тип элемента и число компонентов

У `PF_ChannelDesc` четыре существенных поля: `channel_type`, `name`, `data_type`, `dimension`. `dimension` — число компонентов на пиксель, а не число пикселей или количество каналов, возвращённое enumeration. Имя хранится в массиве `PF_CHANNEL_NAME_LEN+1`; в этой поставке лимит равен 63. [C1:1502–1509]

| SDK-имя семантического типа | Код в полученном header |
|---|---|
| `PF_ChannelType_DEPTH` | `DPTH` |
| `PF_ChannelType_DEPTHAA` | `DPAA` |
| `PF_ChannelType_OBJECTID` | `OBID` |
| `PF_ChannelType_TEXTURE` | `TEXR` |
| `PF_ChannelType_NORMALS` | `NRML` |
| `PF_ChannelType_COVERAGE` | `COVR` |
| `PF_ChannelType_BK_COLOR` | `BKCR` |
| `PF_ChannelType_UNCLAMPED` | `UNCP` |
| `PF_ChannelType_MATERIAL` | `MATR` |

SDK также перечисляет motion vector, node и unknown. Список возможностей API шире меню одного эффекта. Рядом с `DEPTHAA` есть ограниченная оговорка: для 3D precomp в некоторых Artisans, начиная с 16.0. Это не гарантия DPAA для всех источников и не доказательство того, что конкретный AA-переключатель запросил именно его. [C1:1446–1457]

Элементарные типы определены отдельно:

| Тип | Код | Размер компонента в комментарии SDK |
|---|---|---:|
| `PF_DataType_FLOAT` | `FLT4` | 4 байта |
| `PF_DataType_DOUBLE` | `DBL8` | 8 байт |
| `PF_DataType_LONG` | `LON4` | 4 байта |
| `PF_DataType_SHORT` | `SHT2` | 2 байта |
| `PF_DataType_U_BYTE` | `UBT1` | 1 байт |
| `PF_DataType_U_SHORT` | `UST2` | 2 байта |

Нельзя использовать `sizeof(long)` вашей платформы вместо размера компонента `LON4` или считать, что любой Object ID автоматически является `UST2`: тип должен прийти в descriptor. Нормали из трёх `FLT4` занимают 12 байт на пиксель до учёта row padding; это расчёт из `dimension × размер компонента`, описанный в [C1:1462–1478,1527–1548].

**Особенность источника, которую не исправляем молча:** макрос `PF_DataType_RGB` в этом header имеет буквальный код `'RBG '`, хотя его имя — RGB. Использовать SDK-символ, а не переписывать FourCC по ожидаемому написанию. Ни происхождение этого написания, ни поведение импортёра по нему данная сверка не устанавливает. [C1:1479]

## 3. Точные названия callbacks

Имя suite — `kPFChannelSuite1`, строка `PF AE Channel Suite`; версия `kPFChannelSuiteVersion1` равна 1. Объявленная структура — **`PF_ChannelSuite1`**. [C2:92–94,521–561]

| Поле структуры | Назначение |
|---|---|
| `PF_GetLayerChannelCount` | Количество auxiliary-каналов выбранного слоя-параметра |
| `PF_GetLayerChannelIndexedRefAndDesc` | Reference и descriptor для индекса 0…count−1 |
| `PF_GetLayerChannelTypedRefAndDesc` | Reference и descriptor по семантическому `PF_ChannelType` |
| `PF_CheckoutLayerChannel` | Данные в запрошенное время и запрошенном elementary datatype |
| `PF_CheckinLayerChannel` | Завершение использования полученного chunk |

В вводном комментарии того же файла встречаются укороченные перестановки слов вроде `PF_GetLayerIndexedChannelRefAndDesc`. Для кода правильны **поля реально объявленной структуры** из таблицы. Это пример того, зачем читать declarations, а не переносить название из свободного описания. [C2:59–65,528–543]

`param_index` выбирает входной слой-параметр эффекта. `channel_index` выбирает канал внутри источника. Это разные оси. Обе lookup-функции возвращают и код ошибки, и `foundPB`; успешный вызов не следует безусловно приравнивать к найденному каналу.

## 4. Три разных неуспеха

Рекомендуемая логика чтения:

```text
ошибка lookup
  → сохранить код ошибки; descriptor не использовать как успешный результат

lookup успешен, found = false
  → канал не найден данным запросом; не пытаться читать его buffer

lookup успешен, found = true
  → проверить semantic type, datatype и dimension
  → только затем выполнять совместимый checkout
```

Это защитная схема для собственного кода, построенная на раздельных возвращаемых полях [C2]. Она не задаёт универсальное изображение ошибки для всех native effects. Чёрный кадр может быть результатом разных причин; сам по себе он не заменяет descriptor и статус запроса.

Для строгой проверки источника разумно сопоставлять typed lookup с индексным inventory. Это методика Библии, не новое требование SDK: она помогает заметить неправильную карту импортёра, неоднозначные теги и ошибочно выбранный слой.

## 5. Checkout может запросить другой тип

`PF_CheckoutLayerChannel` принимает reference, `what_time`, `duration`, `time_scale`, `data_type` и указатель на `PF_ChannelChunk`. Комментарий говорит, что chunk выделяется в запрошенном типе и имеет chunky-представление. [C2:67–80,545–552]

Поэтому следует различать как минимум три значения: тип в descriptor, тип, переданный в checkout, и тип, вернувшийся в chunk. Формат хранения в EXR — ещё один, внешний уровень. Проверка «в EXR стоит FLOAT, следовательно эффект получил FLT4» недостаточна.

В declaration возле `data_type` стоит комментарий `/* << */`, хотя параметр передаётся по значению и вводное описание называет его запрашиваемым типом. В Библии сохраняем это расхождение как особенность исходника; не меняем сам SDK и не строим контракт только по стрелке.

Для исследования без неявного преобразования разумно запрашивать совместимый тип из descriptor и отдельно проверять returned type. Проверку преобразований нужно задавать как самостоятельный сценарий. Это рекомендация, а не запрет других запросов API.

## 6. Как читать chunk без ошибки stride

`PF_ChannelChunk` содержит `widthL`, `heightL`, `dimensionL`, `row_bytesL`, `data_type`, `dataH` и `dataPV`. Reference является opaque-объектом; его внутреннее содержимое нельзя трактовать как файловый offset или постоянный ID. [C1:1515–1548]

Для interleaved-данных адрес логического компонента вычисляется так:

```text
row(y)       = byte_pointer(dataPV) + y * row_bytesL
pixel(x, y)  = row(y) + x * dimensionL * component_size
component(c) = pixel(x, y) + c * component_size
```

Это формула адресации по полям SDK, **не разрешение читать непроверенный buffer**. До обхода нужно проверить указатель, фактические размеры, тип и dimension; умножения/сложения должны быть защищены от переполнения. Для узкого учебного примера допустимо явно отклонять неподдержанный stride вместо угадывания его смысла. [C1:1527–1548], [C3:231–243]

Не предполагать, что `row_bytesL` всегда равен плотной длине строки. Не переинтерпретировать memory layout `PF_PixelFloat` как layout нормалей: у image world есть alpha/RGB, у auxiliary buffer число компонентов задаётся `dimensionL`.

Макрос `PF_GET_CHANNEL_FLOAT_DATA` проверяет datatype, но не доказывает наличие нужного числа компонентов, подходящей геометрии или достаточного объёма памяти. Это удобство доступа, не полный валидатор. [C3:103–113]

## 7. Checkin обязателен именно для этого интерфейса

Комментарий `PF_CheckinLayerChannel` прямо требует вернуть checked-out канал для предотвращения утечек. Освобождение идёт через suite, а не через пользовательский `free(dataPV)` или dispose чужого `dataH`. [C2:82–87,555–558]

Структура control flow собственного кода должна обеспечивать: успешный checkout → попытка обработки/копирования → checkin даже при ошибке обработки. Указатель или reference на временное содержимое не должен оставаться в кеше после завершения его срока действия. Исключения C++ тоже должны попадать в этот cleanup-путь.

**Не переносить правило из SmartFX:** у `checkin_layer_pixels` другой комментарий — ранний checkin полезен, но не обязателен, а world действует до завершения команды. Это относится к image world SmartFX, не к auxiliary chunk. [C4], [SmartFX](03-SMARTFX.md)

## 8. Глубина и специальное значение

`AE_ChannelSuites.h` определяет `PF_CHANNEL_DEPTH_INFINITY` как `1e7`. Это конечная числовая константа, а не IEEE `+Infinity`. Сам macro не устанавливает, как каждый importer или 3D Channel Extract обрабатывает её, отрицательную глубину, NaN или бесконечности. [C2:90]

Следовательно, в тестовых данных и документации нельзя объединять sentinel, IEEE nonfinite и «канал не найден» в одно состояние. Наши EXR-данные со специальными значениями остаются заданными входами; их обработка native effect требует отдельного наблюдения.

## 9. Что теперь подтверждено для Библии

Полученный SDK подтверждает имена suite/callbacks, поля descriptors/chunks, FourCC `UBT1`/`UST2`/`FLT4`, наличие `DPAA` и правило checkin. Это **сверка интерфейса по исходнику**, а не доказательство вызова определённой функции в ранее записанном рендере.

SDK не содержит здесь исходный алгоритм `Aux_Channel_Extract`; из этой главы не следует полное восстановление его UNCP-ветки, AA или CPU/GPU/MFR-поведения. Такие неизвестные остаются в [исследовательском атласе](../21-BUILTIN-EFFECTS-REVERSE-ENGINEERING/3D-Channel/3D-Channel-Extract/README.md). Разработку отдельного считывателя не продолжаем в рамках этой редакционной задачи.
