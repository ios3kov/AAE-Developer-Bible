# Пиксели, цвет и прозрачность в Effect-плагине

Основа — **приложенный SDK 25.6 build 61**, не предположение о формате картинки на экране. Хэши и диапазоны источников находятся в [реестре сверки](../18-SDK-HEADER-TOOLS/06-PARAMETERS-PIXELS-SDK25.6.md). Пути ниже относительны `Examples/` этой поставки.

Нужно различать четыре уровня: **формат пикселя → расположение буфера → смысл цвета/alpha → преобразования при экспорте**. Совпадение одного уровня не доказывает совпадения остальных. Эта глава объясняет контракт и проектные решения; новый native-render в рамках её написания не выполнялся.

## 1. Что означают 8, 16 и 32 bpc

`Headers/AE_EffectPixelFormat.h:32–36` задаёт три AE-style формата. Структуры компонент находятся в `AE_Effect.h:1359–1381`.

| Формат world | Тип пикселя | Компонента | Номинальный чёрный / белый |
|---|---|---|---|
| `PF_PixelFormat_ARGB32` | `PF_Pixel8` / `PF_Pixel` | `A_u_char` | 0 / 255 |
| `PF_PixelFormat_ARGB64` | `PF_Pixel16` | `A_u_short` | 0 / **32768** |
| `PF_PixelFormat_ARGB128` | `PF_PixelFloat` / `PF_Pixel32` | `PF_FpShort` | 0.0 / 1.0 |

Числа 32/64/128 в именах форматов относятся ко всему четырёхкомпонентному пикселю, а 8/16/32 bpc — к одной компоненте. `PF_Pixel32` здесь является alias float-пикселя, а `PF_PixelFormat_ARGB32` — форматом с 8 битами на канал. Не выбирайте тип по одному фрагменту имени.

В обычных declarations порядок полей — `alpha, red, green, blue`, **не RGBA**. У `PF_Pixel16` предусмотрено условное переименование полей `PF_PIXEL16_RENAME_COMPONENTS`; код с именами `alpha/red/...` предполагает, что этот debug-режим не включён.

### 16-битный AE world — не полный диапазон uint16

В `AE_Effect.h:531–537` допустим диапазон 0…32768; выход за него описан как undefined behavior и не должен покидать плагин. Константы на строках 568–571:

```text
PF_MAX_CHAN8  = 255       PF_HALF_CHAN8  = 128
PF_MAX_CHAN16 = 32768     PF_HALF_CHAN16 = 16384
```

Число 65535 может быть значением unsigned 16-bit данных **другого назначения**, но не становится из-за этого правильным белым в `PF_Pixel16`. Например, auxiliary Object ID и цветовая компонента имеют разные контракты; см. [дополнительные каналы](08-AUXILIARY-CHANNELS.md).

**Оговорка к источнику:** объясняющий комментарий рядом с константами содержит `16834` и `32878` (`AE_Effect.h:550,556`). В этой главе использованы реальные defines и согласующееся объявление ARGB64, а опечатки сохранены в реестре. Исходник SDK не исправлялся.

## 2. Float — не просто более подробные 0…1

`AE_Effect.h:561–562` прямо связывает float с поддержкой значений выше и ниже номинального диапазона; для ARGB128 число 1.0 обозначает белый, а не физический предел типа.

**Правило проектирования:** отдельно решить, сохраняет ли конкретная операция отрицательные RGB, HDR выше 1, нечисловые значения и бесконечности. Не применять clamp ко всему результату только потому, что в 8-битном варианте без него нельзя записать пиксель.

Авторский пример, не алгоритм какого-либо нативного эффекта: для операции `RGB_out = 2 × RGB_in` значение 1.5 должно стать 3.0, если задача заявлена как линейное усиление без ограничения. Превращение результата в 1.0 было бы другой операцией. Политика alpha задаётся отдельно: увеличение яркости не обязательно означает увеличение непрозрачности.

Для NaN/Inf и переполнения числового типа нужен отдельный выбранный контракт. Наличие float-ветки не устанавливает, что плагин корректно обрабатывает каждый специальный битовый шаблон.

## 3. Выбирать ветку по фактическому world

`PF_WorldSuite2::PF_GetPixelFormat` получает указатель на конкретный `PF_EffectWorld` и возвращает `PF_PixelFormat` (`AE_EffectCBSuites.h:430–454`). Это точка выбора 8/16/float, а не чтение подписи настроек проекта или предположение по входному имени файла.

`PF_WORLD_IS_DEEP` проверяет только один бит `PF_WorldFlag_DEEP` (`AE_Effect.h:512–529`). Один boolean не заменяет явное различение трёх форматов.

Рекомендуемая последовательность адаптера:

```text
Получить input/output worlds в разрешённой render-фазе
→ запросить и проверить формат нужных worlds
→ подтвердить поддерживаемое сочетание input/output
→ выбрать тип пикселя и соответствующий callback
→ обработать область, вернуть ошибку или завершённый результат
```

`SmartyPants.cpp:882–928` показывает переключение между ARGB128, ARGB64, ARGB32 и разными iterate callbacks. Это полезный образец dispatch, но не основание считать любой cast безопасным или весь SmartyPants эталоном потокобезопасности. Ограничения образца разобраны в [SmartFX](03-SMARTFX.md).

Одного `PF_OutFlag_DEEP_COLOR_AWARE` недостаточно для заявления float-поддержки: `Skeleton.cpp:80` прямо помечает этот пример как 16 bpc, не 32 bpc. Полный 32-битный путь связан с соответствующими capabilities, SmartFX, форматом world и реальным вычислением, а не только с типом локальной переменной.

## 4. World — это описание изображения, не плоский массив

`PF_EffectWorld` является alias `PF_LayerDef`. В структуре есть data, rowbytes, width/height, extent, pixel aspect и origin (`AE_Effect.h:1594–1637`).

| Поле | Как использовать |
|---|---|
| `data` | Память пикселей в формате данного world; сам объявленный pointer не выбирает float/16/8 |
| `rowbytes` | Шаг между строками в байтах, отдельно для каждого world |
| `width`, `height` | Размер этого буфера, не обязательно всей композиции |
| `extent_hint` | Для источника — область ненулевой alpha; для output — область, требующая обработки, по комментарию header |
| `origin_x`, `origin_y` | Начало буфера в координатах слоя, отмеченное для SmartFX checkouts |
| `pix_aspect_ratio` | Соотношение сторон пикселя полученного слоя |

**Адресная формула** для уже проверенного CPU-буфера:

```text
row_address   = byte_address_of_base + y × rowbytes
pixel_address = row_address + x × sizeof(фактический тип пикселя)
```

Это объяснение адресации, не разрешение писать в произвольный world. Перед циклом проверяются диапазон x/y, ожидаемый тип, доступность data, вместимость строки и отсутствие переполнения арифметики адресов. У input и output могут быть разные strides. Копирование `width × height × sizeof(pixel)` одним блоком без учёта строк может захватить padding или пропустить часть изображения.

Не смешивайте координаты слоя и локальные x/y полученной области. Сначала пересчитайте их с учётом origin и render-запроса. `extent_hint` не увеличивает выделенный буфер и не заменяет SmartFX result rectangles; соответствующий контракт описан в [главе SmartFX](03-SMARTFX.md).

## 5. Получить typed pointer, а не угадать его

В `PF_PixelDataSuite1` есть `get_pixel_data8`, `get_pixel_data16`, `get_pixel_data_float`; переданный `pixelsP0=NULL` означает data самого world. Комментарий предупреждает о NULL при несовпадении глубины (`AE_EffectCBSuites.h:109–130`). Поэтому после успешного вызова нельзя безусловно разыменовывать возвращённый pointer.

В версии 2 отдельно присутствует `get_pixel_data_float_gpu` (`AE_EffectCBSuites.h:133–156`). Наличие отдельной GPU-функции — дополнительная причина не выдавать CPU-цикл за обработчик любой GPU-памяти. Эта глава не специфицирует GPU layout или передачу device memory.

Для простых попиксельных операций предусмотрены iterate suites. Они передают refcon, координаты, входной и выходной пиксели; существуют варианты 8/16/float и варианты с origin. `AE_EffectCB.h:641–656,699–715`; `AE_EffectCBSuites.h:743–777`.

Важно: SDK разрешает распределять iterate по потокам и требует read-only или синхронизированный refcon. Вход разрешено менять только при `PF_WorldFlag_WRITEABLE` (`AE_EffectCB.h:687–695`). **Даже отсутствие MFR-флага не является доказательством, что ваш pixel callback всегда однопоточный.** Не храните в общем refcon несинхронизированные счётчики или «последний обработанный пиксель».

## 6. Нормализация и квантование — явное решение алгоритма

Из объявленных максимумов следуют формулы для допустимых целочисленных кодов:

```text
нормализованное 8-bit значение  = code8  / 255.0
нормализованное 16-bit значение = code16 / 32768.0
```

Это арифметический вывод из SDK-констант, не преобразование между цветовыми пространствами. Деление на максимум само по себе не делает код «линейным светом» и не преобразует профиль.

Для обратной записи нужно выбрать округление, поведение за диапазоном и поведение нечислового входа. Проектная политика для **конечного** нормализованного значения может быть такой:

```text
q = floor(clamp(value, 0, 1) × MAX + 0.5)
```

Она приведена как пример округления к ближайшему для неотрицательного диапазона. Нельзя называть её точным внутренним правилом всех эффектов Adobe. Нельзя также применять её к float-пути незаметно: она одновременно вводит clamp и квантование.

Сопровождающий [`Minimal Gain`](../16-WORKING-TEMPLATES/effect-basic/EffectMain.cpp)
выбирает другую политику: `clamp(input × gain, 0, MAX)` и затем целочисленный cast,
то есть усечение неотрицательной дробной части. Например, code8=1 и gain=1.5 дают
code8=1, не 2. Alpha копируется без усиления. Это 8/16-bpc source example; HDR/float
сценарии этой главы и round-to-nearest формула не являются его реализацией.
Заполненный [Gain evidence plan](../13-TEMPLATES/examples/WORKED-EXAMPLE.md)
должен читаться с этой source policy, а не как доказательство измеренного render.

Полезный контроль: 16384/32768 равно ровно 0.5, а 128/255 — примерно 0.50196. Одинаковые надписи «50% серого» в разных источниках не гарантируют одинаковое нормализованное число. В анализе реального эффекта различайте ожидаемую квантизационную разницу, ошибку математики и дополнительную цветовую обработку.

## 7. Alpha: формула должна соответствовать представлению

SDK явно различает premultiplied и straight при описании `premultiply`; для matte-цвета, отличного от чёрного, есть `premultiply_color` (`AE_EffectCB.h:658–664`). Структура `PF_PixelFloat` сама по себе не содержит полного объяснения цветового происхождения буфера.

Для случая premultiplication чёрным математическая модель:

```text
C_premult = alpha × C_straight
C_straight = C_premult / alpha, если alpha ≠ 0
```

При alpha=0 обратная операция не определена этой формулой. Нужна политика своего алгоритма: что делать со скрытым RGB, что хранить после фильтрации и что считать корректным прозрачным краем. Это нельзя решить простым безусловным делением на alpha.

### Почему нелинейная операция даёт кайму

Авторский численный пример: straight-компонента 0.8 при alpha=0.25 хранится как premult-компонента 0.2. Если выбранная операция — квадрат **straight**-цвета, ожидаемый premult-результат равен `0.25 × 0.8² = 0.16`. Квадрат прямо над 0.2 даёт 0.04 — другую картинку.

Это не рекомендация всегда unpremultiply перед любой операцией. Для линейного однородного усиления RGB при неизменной alpha умножение коммутирует с premultiplication. Для blur/resampling или нелинейных операций надо определить математическую модель и её поведение на границах отдельно.

`PF_FillMatteSuite2` предоставляет `premultiply`, `premultiply_color`, `premultiply_color16`, `premultiply_color_float`. Для forward комментарий задаёт TRUE как преобразование straight → premult, FALSE — обратно (`AE_EffectCBSuites.h:860–910`). Различия аргументов сохраняются: `premultiply` принимает один world, color-варианты имеют source/destination. Не переносите сигнатуру одного варианта на другой по сходству имени.

## 8. Цветовой параметр: не масштабировать восьмибитный swatch вручную

`PF_ColorDef` содержит `PF_UnionablePixel`, но для floating-point цвета есть отдельная `PF_ColorParamSuite1`. Её комментарий устанавливает два существенных свойства: цвет находится в том же рабочем пространстве, что пиксели эффекта; значения могут быть выше и ниже номинального диапазона **даже вне 32-bpc проекта** (`AE_EffectSuites.h:312–333`).

Учебный фрагмент ниже принимает уже приобретённую suite и допустимый текущий параметр. Он не управляет её lifetime и не получает параметр на нужное время вместо вызывающего кода.

```cpp
PF_Err ReadWorkingColor(PF_ColorParamSuite1* suite,
                        PF_ProgPtr effect_ref,
                        const PF_ParamDef* color,
                        PF_PixelFloat* result)
{
    if (!suite || !color || !result || color->param_type != PF_Param_COLOR)
        return PF_Err_BAD_CALLBACK_PARAM;
    return suite->PF_GetFloatingPointColorFromColorDef(effect_ref,
                                                      color, result);
}
```

Соответствующие структуры: `AE_Effect.h:1817–1825`; декларация вызова: `AE_EffectSuites.h:328–331`. Скалярное деление `u.cd.value.red/255` не заменяет этот документированный способ получения float-цвета рабочего пространства. Конечный статус операции определяется возвратом suite; приобретение и освобождение PICA рассматриваются отдельно от цвета.

## 9. Не смешивать working space, показ на экране и экспорт

Поддержка 32 bpc отвечает на вопрос о представлении компонент. Она не отвечает автоматически на вопросы о transfer function, primaries, линейном смешивании или output-профиле. Для конкретного алгоритма нужно зафиксировать, в каком пространстве он работает и какие операции выполняет host до и после него.

**Рекомендация Библии:** не добавлять скрытую степень 2.2, clamp или преобразование в sRGB ради того, чтобы два скриншота «стали похожи». Сначала определить контракт входа/выхода и настройки host. Gamma-кривая художественного эффекта и перевод цветового профиля — разные задачи; имя примера или наличие `pow` не доказывает правильность профиля.

При сравнении сохраняйте отдельно: значение input/параметров, формат рабочего world, проектные color settings, метод выборки, transform/ROI, output-module settings, фактический формат/глубину экспортированного файла и способ его декодирования. File hash отвечает за байты файла; hash декодированных пикселей — за выбранное представление изображения. Это проектный протокол проверки, не описание нового SDK-вызова.

Показательный уже собранный материал: [аудит 3D Channel Extract](../21-BUILTIN-EFFECTS-REVERSE-ENGINEERING/3D-Channel/3D-Channel-Extract/EVIDENCE-AUDIT-2026-09-30.md) сохранил различие float PSD и layer-space sampleImage. Причина в том аудите не установлена. Нельзя переименовывать расхождение в доказанную gamma-коррекцию; сравнение AA-пар одного формата и сравнение разных output-путей отвечают на разные вопросы.

Экспортированный PNG с unsigned 16-bit компонентами и `PF_Pixel16` внутри AE не обязаны иметь один числовой масштаб. Сначала читается реальный header файла, затем устанавливается output-контракт; слово «16 бит» не разрешает безусловный byte-for-byte memcpy между ними.

## 10. Память и область записи — часть корректности цвета

Host-owned input/output не освобождаются как самостоятельно созданный scratch-world. `AE_EffectCB.h:666–672` требует dispose для созданного world и запрещает освобождать чужие worlds. В `PF_WorldSuite2` пары создания/освобождения имеют точные имена `PF_NewWorld`/`PF_DisposeWorld` (`AE_EffectCBSuites.h:436–446`).

Неправильный row stride, запись за ROI или использование pointer после checkin способны выглядеть как случайные полосы, грязный alpha либо цветовой шум. Это диагностическая гипотеза, не готовый диагноз по одному скриншоту. Начинайте с формата, размеров, lifetime и диапазона записи, прежде чем менять математику ради подавления артефакта.

Дополнительные каналы нельзя получить обычным reinterpret_cast RGBA: у них собственные datatype, dimension, row stride и checkout/checkin. Этот контракт вынесен в [отдельную главу](08-AUXILIARY-CHANNELS.md).

## 11. Минимальный набор проверок пиксельного алгоритма

Ниже — проектируемая приёмка, не новые выполненные тесты.

| Вход или сравнение | Что проверяет |
|---|---|
| Neutral ramp с чёрным, серединой и белым | Масштаб 255/32768/1.0 и округление |
| Разные R/G/B и alpha | Перепутанные компоненты и случайное изменение alpha |
| Отрицательный RGB и HDR >1 в float | Непреднамеренный clamp |
| Полностью прозрачный и дробно-прозрачный цветной край | Деление на ноль, скрытый RGB, модель фильтрации |
| Impulse/checker и нечётная ширина | Смещения, границы, stride |
| Одинаковый участок full frame и ROI с ненулевым origin | Согласованность координат и зависимостей |
| Input/output с разными допустимыми rowbytes | Неправильное предположение об общей раскладке |
| World-данные и экспорт при зафиксированных настройках | Отделение вычисления эффекта от output processing |

Для float задайте абсолютный и относительный допуски вместе с масштабом значений; для NaN/Inf и signed zero — отдельное правило сравнения. Это выбранная методика конкретного теста, не универсальный допуск Adobe. Совпадение одного кадра не закрывает [потокобезопасность/MFR](04-MFR-THREAD-SAFETY.md).

## Калибровка output и exceptional values

Перед algorithm test проверить identity-control всей цепочки: source → effect
world → output module → файл → независимый decoder. Ramp/impulse и разные
R/G/B/alpha выявляют scale, offset и alpha representation. Записать actual decoder
format, working/output profiles и transforms. 32-bpc project → RGBA16 unsigned
export не проверяет сохранение native HDR/NaN; equality export относится только
к этому export. `sampleImage` с area sampling также не exact raw pixel accessor.

Для float заранее выбрать numeric или bitwise policy: +0/−0 могут быть numeric
equal, но bytes различны; NaN требует class/payload policy; ±Inf — sign/class;
finite values — explicit absolute/relative tolerance либо exact bytes в matching
environment. Shortcut `x*1 → x` не доказывает exceptional-bit preservation.
Fast-math/FMA/reassociation входят в identity сравнения.

Original artifact comparison сохранять отдельно от unchanged-source rebuild
matching toolchain. Control помогает локализовать delta, но не устанавливает
причину различия старого artifact автоматически. Sampling связан со spatial/temporal
walkthrough в [SmartFX](03-SMARTFX.md); IDs/depth не обрабатывать как RGB.

## Итоговая схема обработки

```text
Фактический world и формат
→ typed access + размеры/stride/origin
→ явно выбранная модель RGB и alpha
→ вычисление без скрытого изменения диапазона
→ запись только допустимой области
→ проверка результата отдельно от экранного показа и экспорта
```
